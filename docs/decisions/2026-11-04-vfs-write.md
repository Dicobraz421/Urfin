# Запись в схемы — методами `Vfs`, сетевой крейт без зависимости от операций

(владелец, 2026-11-03, класс B) В F03-07 (#288) операции SFTP писали через `urfin_ops::RemoteFs` и реестр `Remotes` в `AppState.ext`, объявленные в ops, — `urfin-net` зависел от `urfin-ops`, слой был перевёрнут. Будущий `Vfs::writer() -> VfsWriteTxn` (транзакция под архивы) запись с произвольного места не даёт, а она нужна докачке.

Выбрано: **запись — в `urfin_vfs::Vfs`**. У всех схем есть методы записи, по умолчанию «не поддерживается» (`VfsError::NoWrite`). Один путь для сети и позже для архивов; сетевой крейт от операций не зависит.

- Методы `Vfs` (блокирующие, из потоков job): `open_write(p, from) -> Box<dyn VfsWrite>` (создать или обрезать; с байта `n` — докачка, дописывание), `VfsWrite::finish` (сброс на носитель — `fsync`, если умеет, — и закрытие с ответом), `mkdir`, `remove` (файл, ссылка, пустой каталог), `rename(from, to, replace)` (поверх — атомарно, если умеет, иначе удаление и rename с записью в лог), `set_meta(mode, mtime)`, `link(at) -> Link` («ждёт связи», по умолчанию `Up`), `transfer_channels()` (по умолчанию 1).
- Ops пишет в схему через backend из реестра VFS (`Schemes` в `AppState.ext`) — тот же, что читает. Схема с `Caps::READ_ONLY` — отказ до задачи («запись не поддерживается»); схема без записи без этого флага — та же понятная ошибка в отчёте задачи. Виртуальные схемы (`Caps::VIRTUAL`: `du:`, `pkg:`) и адреса внутри архива — по-прежнему не через этот путь.
- `urfin_ops::RemoteFs`, `Remotes`, `SftpOps` удалены; backend `sftp` (`SftpFs`) реализует запись в своём `Vfs`. `urfin-ops` у `urfin-net` — только dev-зависимость интеграционных тестов на `testsrv`.
- Локальная ФС в ops пишет сама, как раньше (быстрые пути `CopyFileEx` и др.); перевод на `Vfs` — не в этой волне.
- `VfsWriteTxn` для архивов — надстройка позже, над теми же методами (см. CONTRACTS «VFS и операции»).
