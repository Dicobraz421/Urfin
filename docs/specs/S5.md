## 0. Ключевые решения

- **Решение:** движок выбирается для каждого файла по таблице стратегий `(класс носителя src×dst, тот же том, возможности ФС, размер, опции) → Engine`. Значения по умолчанию берутся из бенчей S5-25, конфиг `[ops.strategy]` может их переопределить.
  **Почему:** «быстрее ОС» на одном типе носителя и медленнее на другом не годится. Только измеренная таблица даёт выигрыш везде, а новый движок добавляется без переписывания конвейера.
- **Решение:** у job свои потоки: координатор и N воркеров через `Runtime::spawn_dedicated`. На `Lane::Bulk` уходят только короткие задачи. Потоки завершаются вместе с job.
  **Почему:** в Bulk 2 потока. Долгая копия или координатор, ждущий `ask`, заняли бы их, и встала бы запись сессии. После job в простое 0 потоков (бюджет «0% CPU»). Нужно подтверждение S0 (запрос 1).
- **Решение:** обход дерева идёт параллельно со стартом копирования. Bounded-очередь работ (64k элементов) даёт бэкпрешер, `items_total` растёт по ходу, UI показывает «≥ N» до конца скана.
  **Почему:** первый байт пишется через <100 мс вместо «Подсчёта» Explorer, память ограничена при любом размере дерева.
- **Решение:** конфликт не останавливает job. Файл паркуется в очередь вопросов, воркеры продолжают с остальными. Отвечать на вопросы по одному через `JobHandle::ask` (S1) будет координатор, но заблокирован только он сам. Существование целей выясняется заранее: каждый уже существовавший каталог назначения листингуется один раз, поэтому конфликт виден до копирования данных. Финальная гарантия от гонок — эксклюзивное создание (`CREATE_NEW`/`O_EXCL`/`RENAME_NOREPLACE`).
  **Почему:** ноль модальных окон, ни одного лишнего прочитанного байта при «Пропустить», нет TOCTOU.
- **Решение:** признак завершённости файла — mtime, равный исходному. Его выставляем последним действием перед close/rename. Файлы ≥1 МиБ и любые перезаписи идут через temp + атомарный rename. Мелкие новые файлы пишутся сразу под финальным именем.
  **Почему:** temp+rename для 100k мелких файлов удваивает метаданные. Признак по mtime бесплатен. Восстановление сводится к повторному запуску с политикой `SkipIdentical`, и пофайловый журнал не нужен.
- **Решение:** persist-лог — один append-only файл на job: запрос, фаза, счётчики, созданные temp-файлы и корни назначения. Это не пофайловый журнал. fsync только на заголовке и на End.
  **Почему:** накладные расходы ≈0, а восстановление полное: идемпотентный повтор плюс чистка temp.
- **Решение:** Windows: `CopyFile2` — базовый движок для сети (copychunk/ODX), для файлов с EA/reparse и как fallback. Собственные движки: block clone через `FSCTL_DUPLICATE_EXTENTS_TO_FILE`, быстрый путь для мелких файлов (с ADS), небуферизованный overlapped-поток для крупных и для verify. macOS: `clonefile` (в том числе целого дерева одним вызовом) и `fcopyfile`. Linux: `FICLONE` → `copy_file_range` → read/write.
  **Почему:** где ОС уже оптимальна (серверное копирование, ODX), используем её. Где проигрывает (накладные расходы на файл, отсутствие хэша на лету, последовательная обработка), используем своё.
- **Решение:** параллелизм задаётся по классу носителя: NVMe 16, SATA SSD 8, HDD 1, SMB 8, USB-flash 2, неизвестный 4. Число воркеров на ходу подстраивает AIMD по пропускной способности (окно 500 мс). Задачи на одном HDD автоматически встают в очередь.
  **Почему:** на SSD выигрыш даёт параллельность, на HDD она убивает скорость поиском. Фиксированное N везде неверно.
- **Решение:** удаление дерева: параллельные воркеры по каталогам, удаление относительно дескриптора каталога. На Windows — POSIX-семантика (`FILE_DISPOSITION_FLAG_POSIX_SEMANTICS|IGNORE_READONLY_ATTRIBUTE`), на unix — `unlinkat(dirfd)`. Каталог удаляется, когда счётчик его детей доходит до 0.
  **Почему:** нет пофайлового разбора пути, нет отдельного прохода снятия read-only, нет ожидания «delete pending» на NTFS.

## 2. API

### 2.1 Запрос и опции

```rust
#[derive(Clone, Debug, Serialize, Deserialize)]
pub struct OpRequest {
    pub kind: OpKind,
    pub base: Location,                  // каталог источников (Targets::base)
    pub items: Vec<CompactString>,       // имена в base (Targets::items); пусто для Mkdir
    pub dest: Option<Location>,          // Copy/Move/Link/Sync
    pub opts: OpOptions,
}

#[derive(Clone, Debug, Serialize, Deserialize)]
pub enum OpKind {
    Copy, Move, Delete, Trash,
    Mkdir { path: CompactString },                     // "a/b/c" и "x;y" (Far)
    Rename { to: CompactString },
    MultiRename(RenameSpec),
    SetAttrs(AttrChange),
    Link(LinkKind),                                    // Hard | Symbolic | Junction (Windows)
    Compare(CompareMode),                              // Quick | Content
    Sync(SyncSpec),
}

/// Семантика dest (как в Far): существующий каталог → «внутрь»;
/// один элемент и dest не существует без завершающего разделителя → новое имя;
/// завершающий разделитель → создать каталог и положить внутрь.
pub fn resolve_dest(req: &OpRequest, dest_exists: Option<EntryKind>) -> DestMode;
pub enum DestMode { Into(Location), RenameTo(Location) }

#[derive(Clone, Debug, Serialize, Deserialize)]
#[serde(default)]
pub struct OpOptions {
    pub conflict: ConflictPolicy,        // Ask
    pub dirs: DirPolicy,                 // Merge
    pub errors: ErrorPolicy,             // Ask (после авто-ретраев)
    pub verify: Verify,                  // Off
    pub preserve: Preserve,              // TIMES|ATTRS|STREAMS|XATTRS
    pub links: LinkMode,                 // Preserve
    pub filter: Option<Mask>,
    pub priority: Priority,              // Normal
    pub engine: EngineOverride,          // Auto
    pub durability: Durability,          // Fast
    pub limit_bps: Option<NonZeroU64>,
    pub workers: Option<NonZeroU8>,      // None = авто
    pub cloud: CloudPolicy,              // Hydrate
    pub queue: QueueMode,                // Auto (по устройству) | Now
}

#[derive(Clone, Copy, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub enum ConflictPolicy {
    Ask, Overwrite, Skip,
    OverwriteIfNewer,                    // mtime src > dst (с учётом точности ФС)
    OverwriteIfDiffers,                  // size или mtime различаются
    SkipIdentical,                       // size и mtime равны → skip, иначе Ask (восстановление, sync)
    RenameNew(RenameScheme),             // "name (2).ext"
    RenameExisting(RenameScheme),        // старый → "name.bak~N"
}
#[derive(Clone, Copy, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub enum RenameScheme { Counter, Timestamp }
pub enum DirPolicy { Merge, Ask, Skip }
pub enum ErrorPolicy { Ask, Skip, Abort }
pub enum Verify { Off, Size, Hash(HashAlgo) }          // Size = размер + успешный fsync
pub enum HashAlgo { Xxh3_128, Blake3 }
bitflags! { pub struct Preserve: u8 { TIMES, ATTRS, STREAMS /*ADS*/, XATTRS, ACL, OWNER, BIRTHTIME } }
pub enum LinkMode { Preserve, Follow, Skip }
pub enum Priority { Low, Normal, High }
pub enum EngineOverride { Auto, NoClone, Os, Stream, Unbuffered }
pub enum Durability { Fast /*устойчиво к падению приложения*/, Safe /*fsync на файл, к потере питания*/ }
pub enum CloudPolicy { Hydrate, Skip }
pub enum QueueMode { Auto, Now }
```

### 2.2 Проблемы (конфликты и ошибки), парковка

```rust
#[derive(Copy, Clone, Eq, PartialEq, Hash, Debug)] pub struct IssueId(pub u32);

#[derive(Clone, Debug)]
pub struct Issue {
    pub id: IssueId,
    pub kind: IssueKind,
    pub src: Option<ItemMeta>,           // имя, размер, mtime, attrs
    pub dst: Option<ItemMeta>,
    pub op: ItemOp,                      // Copy/Move/Delete/... для текста
    pub temp: Option<PathBuf>,           // данные уже скопированы в temp (гонка при rename)
}

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
pub enum IssueKind {
    Exists,          // файл назначения существует
    TypeMismatch,    // файл ↔ каталог
    SameFile,        // src и dst — один объект (hardlink/тот же путь)
    ReadOnlyTarget,
    InvalidName,     // недопустимо на ФС назначения (":", "CON", NFD-коллизия, регистр)
    TooLarge,        // >4 ГиБ на FAT32
    LowSpace,
    NoTrash,         // элемент нельзя в корзину (сеть, слишком большой, длинный путь)
    Cloud,           // облачный плейсхолдер, будет скачан
    Io(IoClass),     // Permission, Sharing, Busy, Network, NotFound, Other
}

/// Ответ на проблему: id выбора из PromptSpec.choices.
pub enum Resolution { Overwrite, Skip, RenameNew, RenameExisting, Retry, NewName(String), DeletePermanently, Abort }
```

Набор вариантов выбора зависит от `IssueKind`:

| IssueKind | варианты (клавиша) | «для всех» |
|---|---|---|
| Exists | Заменить (R), Пропустить (S), Переименовать (N), Заменить если новее (W), Другое имя… (E), Отмена (Esc) | да |
| TypeMismatch | Пропустить, Другое имя…, Отмена | да |
| ReadOnlyTarget | Заменить, Пропустить, Отмена | да |
| InvalidName | Исправить автоматически (`:`→`_`, суффикс для коллизии), Другое имя…, Пропустить | да |
| TooLarge / Cloud | Пропустить, Продолжить (Cloud), Отмена | да |
| LowSpace | Повторить, Пропустить файл, Отмена | нет |
| NoTrash | Удалить насовсем, Пропустить, Отмена | да |
| Io | Повторить, Пропустить, Пропустить все такие, Отмена | да (по `IoClass`) |

### 2.3 Прогресс, события, отчёт

- Прогресс — атомики `Progress` из S1. Воркеры увеличивают `bytes_done` по чанкам (≤4 МиБ) и `items_done` по завершённым файлам. `set_current` вызывается для файлов ≥1 МиБ или не чаще раза в 100 мс.
- Дополнительно (запрос к S0 №3): `phase` (Scan/Transfer/Verify/Finalize/Recover), `total_final`, `parked`.
- Сообщения `Msg` в core шлются только на редкие события:
  - `OpsMsg::Touched(Vec<Location>)` — каталоги назначения/источника, не чаще 1 раза/с на таб → `panel.refresh`;
  - `OpsMsg::Finished(JobId, Arc<Report>)` — итог, плюс `Toast`, если job дольше 2 с и окно не в фокусе.
- Скорость и ETA считает UI по двум снапшотам (EMA 3 с). ETA до `total_final` показывается как «≥».

```rust
#[derive(Clone, Debug, Default)]
pub struct Report {
    pub summary: JobSummary,             // S1: items, bytes, skipped, errors
    pub cloned: u64, pub renamed_fast: u64, pub verified: u64,
    pub failed: Vec<FailedItem>,         // ≤10k, остальное — счётчиком
    pub elapsed: Duration, pub peak_bps: u64,
    pub engines: SmallVec<[(Engine, u64 /*файлов*/); 6]>,   // для бенчей и отладки
}
pub struct FailedItem { pub path: PathBuf, pub op: ItemOp, pub error: Arc<str>, pub class: IoClass }
```

## 3. Конвейер

```
submit ─► DeviceGate(очередь устройства, приоритет) ─► Coordinator (dedicated)
   Coordinator: plan() ─► Walker[w] ──WorkQueue(bounded 64k)──► Worker[N] ──► Finalizer
                    │            │                                   │            │
                    │            └ mkdir каталогов назначения        │            └ post-order: dir times/attrs, rmdir (move), rename temp
                    │                (до постановки детей)           └ Issue → ParkQueue ─► Coordinator: ask() по одному
                    └ VolumeInfo src/dst, стратегия, проверка места
```

### 3.1 План (coordinator, первые миллисекунды)

1. Для `base` и `dest` вызывается `VolumeInfo::of(path)` (кэш по корню тома, TTL 30 с), см. §3.2.
2. Быстрые пути целиком, без обхода:
   - Move на том же томе → rename каждого top-level элемента (§4.5);
   - Copy каталога на том же APFS-томе, когда dest не существует, нет filter и verify → `clonefile` дерева (§4.1);
   - Delete/Trash → свои конвейеры (§4.6, §4.7).
3. Проверка места: если сумма размеров top-level файлов известна сразу (выделение из `Targets` даёт size файлов), сверяем с местом сейчас, остальное проверяется по ходу (§4.11).
4. Определяется число воркеров (§3.3), запускаются walker и воркеры.

### 3.2 Определение носителя (`VolumeInfo`)

```rust
pub struct VolumeInfo {
    pub id: VolumeId,            // Windows: 64-бит serial (FileIdInfo); unix: st_dev (+ f_fsid)
    pub root: PathBuf,
    pub fs: FsKind,              // Ntfs, Refs, Fat32, ExFat, Apfs, Hfs, Ext4, Btrfs, Xfs, Zfs, Smb, Nfs, Fuse, Other
    pub media: Media,            // Nvme, Ssd, Hdd, Net, Usb, Unknown
    pub caps: VolCaps,           // CLONE, POSIX_DELETE, SPARSE, ADS, XATTR, CASE_SENSITIVE, NORM_INSENSITIVE, TRASH
    pub cluster: u32,
    pub time_res_ns: u32,        // 100 (NTFS), 1 (APFS/ext4), 10_000_000 (exFAT), 2_000_000_000 (FAT)
}
```

| ОС | Шаги |
|---|---|
| Windows | 1. `GetVolumePathNameW`, затем `GetVolumeNameForVolumeMountPointW`. 2. `GetDriveTypeW` (`DRIVE_REMOTE`→Net, `DRIVE_REMOVABLE`→Usb). 3. `GetVolumeInformationW`: имя ФС и флаги `FILE_SUPPORTS_BLOCK_REFCOUNTING`→CLONE, `FILE_SUPPORTS_POSIX_UNLINK_RENAME`, `FILE_NAMED_STREAMS`, `FILE_CASE_SENSITIVE_SEARCH`. 4. `CreateFileW("\\.\Volume{…}", 0, …)` → `IOCTL_STORAGE_QUERY_PROPERTY`: `StorageDeviceSeekPenaltyProperty` (`IncursSeekPenalty`→Hdd), `StorageAdapterProperty.BusType` (`BusTypeNvme`→Nvme, `BusTypeUsb`→Usb). 5. Если у тома несколько экстентов (`IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS`), берётся худший класс. 6. Кластер — `GetDiskFreeSpaceW`. |
| macOS | 1. `statfs`: `f_fstypename` (apfs/hfs/smbfs/nfs/msdos/exfat), `MNT_LOCAL`, `f_fsid`. 2. `getattrlist(ATTR_VOL_CAPABILITIES)`: `VOL_CAP_INT_CLONE`, `VOL_CAP_FMT_CASE_SENSITIVE`. 3. Носитель через IOKit: от `IOMedia` по BSD-имени вверх до `IOBlockStorageDevice`, ключ «Device Characteristics/Medium Type» (`Rotational`→Hdd, иначе Ssd). Внутренний диск Apple Silicon → Nvme без запроса. Protocol USB/Thunderbolt → Usb/Ssd. |
| Linux | 1. `statx`: `stx_dev_major/minor`, затем `/sys/dev/block/M:m` (для раздела — родитель) → `queue/rotational`; имя `nvme*`→Nvme; `removable`/транспорт usb → Usb. 2. `statfs.f_type`: NFS/SMB2/CIFS/FUSE → Net или Other. 3. CLONE — для btrfs/xfs/bcachefs/ocfs2 предполагается, затем проверяется первым `FICLONE` (кэш результата на том). |

Тот же том: равенство `VolumeId`. Linux/btrfs: у сабволюмов разный `st_dev`, но reflink между ними работает. Поэтому для btrfs решает `FICLONE`, а не сравнение id. `EXDEV` у rename → межтомный путь.

### 3.3 Число воркеров и AIMD

- Старт: `n0 = min(table[src.media], table[dst.media])`, где таблица — NVMe 16, Ssd 8, Hdd 1, Net 8, Usb 2, Unknown 4. Только для clone/rename/delete на SSD: ×2 (это чистые метаданные).
- AIMD каждые 500 мс по `bytes+items×4КиБ` в секунду:
  - рост >5% → `n += 1` (до `2×n0`, не выше `max_threads` минус занятые);
  - падение >15% → `n = max(1, n×3/4)`.
  - Для Hdd выключено (фиксировано 1).
- Лишние воркеры паркуются на condvar, поэтому «сжатие» не убивает потоки.
- `DeviceGate`: семафор на физическое устройство (Windows — номер диска из `IOCTL_STORAGE_GET_DEVICE_NUMBER`, unix — whole-disk dev). Job, которой не хватило слота (`device_jobs`), стоит в `Queued`. Приоритет High обгоняет Normal в очереди, но не вытесняет запущенные. `ops.run_now` обходит gate.

### 3.4 Обход (walker)

- Перечисление собственное, в `sys`, без `std::fs::read_dir` + `metadata`:
  - Windows: `NtQueryDirectoryFile(FileFullDirectoryInformation)` относительно handle каталога, буфер 64 КиБ. Дает size, times, attrs и **EaSize** без открытия файла.
  - macOS: `getattrlistbulk` (name, objtype, size, times, flags, linkcount).
  - Linux: `getdents64` через `rustix::fs::Dir` + `statx(AT_STATX_DONT_SYNC)` только для DT_UNKNOWN и файлов (size/mtime). Это batch на дескрипторе каталога.
- Порядок: DFS по каждому источнику. Каталоги ставятся в очередь раньше своих файлов, mkdir делает walker синхронно, до постановки детей. Мелкие файлы одного каталога уходят пачкой (≤64 шт.) одной работой. На SSD walker параллелен (2–4 потока, work-stealing по подкаталогам), на HDD — 1.
- Узлы дерева: `Arc<DirNode { name, parent: Option<Arc<DirNode>>, pending: AtomicU32, meta }>`. Путь собирается по цепочке только при открытии (на Windows открытие идёт относительно handle родителя, путь не нужен). Память — O(глубина × ширина фронта).
- filter (`Mask`) применяется к файлам при обходе. Каталоги не фильтруются.
- Ссылки при обходе не разыменовываются. `LinkMode::Follow` → цикл отслеживается по (VolumeId, FileId).

### 3.5 Воркер

Берёт работу, запрашивает у стратегии `Engine`, выполняет, делает commit (§6.1), уменьшает `pending` родителя. При `pending == 0` и завершённом обходе каталога родитель уходит в Finalizer.

`checkpoint()` вызывается между файлами и между чанками (≤4 МиБ). Внутри `CopyFile2` callback блокируется на паузе, при отмене возвращает `COPYFILE2_PROGRESS_CANCEL`.

### 3.6 Finalizer

Работает в post-order, отдельной лёгкой очередью в потоке координатора:
- выставляет times/attrs каталогу после всех детей (иначе запись детей сбивает mtime каталога);
- для Move: `rmdir` пустого источника; если в нём остался запаркованный или пропущенный ребёнок, каталог не удаляется;
- выполняет отложенные rename.

## 4. Каталог оптимизаций: алгоритмы по ОС

### 4.1 Копия на том же томе (clone)

Условие: тот же том (или btrfs-проба), `caps.CLONE`, `verify` ≠ Hash (у клона нечего проверять, отчёт помечает файлы `cloned`), `engine` ≠ NoClone.

| ОС | Алгоритм | Fallback |
|---|---|---|
| Windows (ReFS, Dev Drive) | 1. `CreateFileW(tmp, GENERIC_WRITE…, CREATE_NEW)`. 2. Если src sparse → `FSCTL_SET_SPARSE` на dst. 3. Integrity streams: `FSCTL_GET_INTEGRITY_INFORMATION` (src) → `FSCTL_SET_INTEGRITY_INFORMATION` (dst), состояние должно совпадать. 4. `SetFileInformationByHandle(FileEndOfFileInfo, round_up(size, cluster))`. 5. Цикл `FSCTL_DUPLICATE_EXTENTS_TO_FILE` кусками по 1 ГиБ (лимит <4 ГиБ на вызов, выравнивание по кластеру). 6. EOF = точный size. 7. Times/attrs, затем rename (§6.1). ADS копируются отдельно (`FileStreamInfo` → тот же клон на поток). | `ERROR_NOT_SUPPORTED`, `ERROR_BLOCK_TOO_MANY_REFERENCES`, несовпадение integrity → `CopyFile2` (на 24H2+ он сам клонирует, где может) |
| macOS (APFS) | Файл: `clonefile(src, tmp, CLONE_NOFOLLOW)` (данные, xattrs, ACL и times копируются атомарно), затем rename. **Каталог целиком**, если dest не существует, нет filter, LinkMode=Preserve: `clonefile(src_dir, dst_dir)` — всё дерево одним вызовом. Прогресс: items_done += итог (подсчёт после, фоново, для отчёта). | `ENOTSUP`/`EXDEV` → `fcopyfile` |
| Linux (btrfs, xfs reflink, bcachefs) | `ioctl(FICLONE)` на tmp-fd от src-fd. Times/xattrs отдельно. | `EOPNOTSUPP`/`EXDEV`/`EINVAL` → `copy_file_range` (§4.3) |

### 4.2 Много мелких файлов (< `small_file`, 1 МиБ)

- Параллельные воркеры (§3.3), пачки по каталогу, открытие относительно handle/dirfd каталога.
- Windows, собственный быстрый путь (если `EaSize == 0`, не reparse, не облачный):
  1. `NtCreateFile(src, FILE_READ_DATA|SYNCHRONIZE, FILE_SEQUENTIAL_ONLY, RootDirectory=hdir)`, `ReadFile` целиком в thread-local буфер 1 МиБ.
  2. Для NTFS — `GetFileInformationByHandleEx(FileStreamInfo)` на открытом handle: есть ли именованные потоки (Zone.Identifier — Mark-of-the-Web — копируется обязательно).
  3. `NtCreateFile(dst, FILE_CREATE)` → `WriteFile` → потоки → `SetFileInformationByHandle(FileBasicInfo)` (times+attrs, последним) → close.
  4. Всё это без temp, признак завершённости — mtime (§6.1).
  Иначе → `CopyFile2`. Порог и выигрыш подтверждает бенч S5-14. Если own ≤ CopyFile2+10%, по умолчанию остаётся CopyFile2.
- macOS: `openat`/`read`/`openat(O_CREAT|O_EXCL)`/`write`, затем `fcopyfile(COPYFILE_METADATA)` или `fsetxattr` (если `listxattr` ≠ пусто), `futimens` + `fsetattrlist(birthtime)`.
- Linux: `openat` + `copy_file_range` (для мелких — один вызов) → `futimens` (последним). xattrs через `flistxattr`, только если ФС их поддерживает.
- Нигде нет per-file fsync в режиме Fast. В режиме Safe: `FlushFileBuffers`/`F_FULLFSYNC`/`fdatasync` перед установкой mtime.

### 4.3 Крупные файлы

| ОС | Движок по умолчанию | Детали |
|---|---|---|
| Windows | `Stream` (до `large_file`) или `Unbuffered` (≥256 МиБ), либо `CopyFile2` — по таблице из бенча | **Unbuffered**: оба handle `FILE_FLAG_NO_BUFFERING\|FILE_FLAG_OVERLAPPED`; буферы `VirtualAlloc` (выравнивание по странице ≥ сектор), 4×8 МиБ в полёте (кольцо: чтение i+1..i+3 при записи i); prealloc `FileAllocationInfo`; хвост пишется округлённым до сектора, затем `FileEndOfFileInfo` = точный размер. **Диапазоны** (NVMe/SMB, файл ≥1 ГиБ): 2–4 воркера пишут непересекающиеся куски по 64 МиБ (`WriteFile` с OVERLAPPED.Offset). `CopyFile2` с `COPY_FILE_NO_BUFFERING` — fallback. |
| macOS | `fcopyfile(COPYFILE_DATA\|COPYFILE_DATA_SPARSE)` или свой `Stream` при verify | Свой: `fcntl(F_NOCACHE,1)` на обоих fd, `F_RDADVISE`, `F_PREALLOCATE` (`F_ALLOCATECONTIG`, затем `F_ALLOCATEALL`) + `ftruncate`; 2 потока (reader/writer) × 8 МиБ буферы |
| Linux | `copy_file_range` циклом по 1 ГиБ | Сначала `fallocate(fd,0,0,size)` (при `EOPNOTSUPP` пропускается; glibc `posix_fallocate` не используется — он пишет нули). `copy_file_range` вернул 0 до size, `EXDEV`/`ENOSYS`/`EINVAL` → read/write 8 МиБ с `posix_fadvise(SEQUENTIAL)` на src, `sync_file_range(WRITE)` + `fadvise(DONTNEED)` каждые 64 МиБ на dst (иначе обвал из-за грязных страниц) |

Sparse: Windows — `FSCTL_QUERY_ALLOCATED_RANGES` и копирование только диапазонов данных (CopyFile2: `COPY_FILE_ENABLE_SPARSE_COPY`, Win11 22H2+). unix — `lseek(SEEK_DATA/SEEK_HOLE)`.

### 4.4 «Подсчёт» перед копией

Отдельного прохода нет: §3.4 стримит работу, `items_total`/`bytes_total` растут, `total_final = true` после обхода. Проверка места идёт по ходу (§4.11).

### 4.5 Перемещение

- Тот же том, то есть один `VolumeId`:
  - Windows — `SetFileInformationByHandle(FileRenameInfoEx, FILE_RENAME_FLAG_POSIX_SEMANTICS [|REPLACE_IF_EXISTS при Overwrite] [|IGNORE_READONLY_ATTRIBUTE])` на handle, открытом с `DELETE`;
  - macOS — `renamex_np(RENAME_EXCL)`;
  - Linux — `renameat2(RENAME_NOREPLACE)`.
  - Каталог переносится одним вызовом. Если целевой каталог существует → Merge: рекурсивно переносятся дети, пустые источники удаляются в Finalizer. Смена только регистра на нечувствительной ФС — прямой rename (Windows/macOS это поддерживают).
- Межтомное: потоковое copy + delete по файлу. Источник файла удаляется сразу после commit его копии. При Verify=Hash — после readback, в режиме Safe — после fsync. Место освобождается постепенно, прерванный move консистентен: в источнике остаётся ровно нескопированное.
- `EXDEV` у rename (bind-mount, сабволюм) → межтомный путь (с clone, если доступен).

### 4.6 Удаление дерева (насовсем)

| ОС | Алгоритм |
|---|---|
| Windows | Перечисление `NtQueryDirectoryFile` по handle каталога. Файл: `NtCreateFile(DELETE\|SYNCHRONIZE, FILE_OPEN_REPARSE_POINT, RootDirectory=hdir)` → `SetFileInformationByHandle(FileDispositionInfoEx, DELETE\|POSIX_SEMANTICS\|IGNORE_READONLY_ATTRIBUTE)` → close. Имя исчезает сразу, каталог можно удалить, даже пока чужой процесс держит файл открытым. Fallback (FAT/exFAT, `ERROR_INVALID_PARAMETER`/`NOT_SUPPORTED`): снять READONLY → `FileDispositionInfo`. Ссылки и junction удаляются как ссылки, без захода внутрь. |
| macOS / Linux | `openat(O_DIRECTORY\|O_NOFOLLOW)` → Dir → `unlinkat(dirfd, name, 0)`, каталоги — `unlinkat(AT_REMOVEDIR)`. На macOS read-only флаги (`uchg`) → `fchflags` при EPERM. |

Параллельность: воркер забирает каталог целиком. Подкаталоги идут в общую очередь, у каждого `DirNode.pending`. Последний ребёнок удаляет родителя. Прогресс считается по items. Bytes для delete не используются.

### 4.7 Корзина

| ОС | Алгоритм |
|---|---|
| Windows | Выделенный STA-поток (`CoInitializeEx(APARTMENTTHREADED)`). Один `IFileOperation` на job: `SetOperationFlags(FOF_NO_UI \| FOFX_RECYCLEONDELETE \| FOFX_EARLYFAILURE)`, затем `DeleteItems(IShellItemArray всех top-level элементов)` одним пакетом, затем `PerformOperations`. Advise `IFileOperationProgressSink`: `UpdateProgress` → атомики. В `PreDeleteItem` проверяется флаг `TSF_DELETE_RECYCLE_IF_POSSIBLE`: если его нет, элемент был бы удалён насовсем (слишком большой, сеть) → `E_ABORT`, элемент → Issue `NoTrash`, пакет перезапускается без него. `PostDeleteItem`: `psiNewlyCreated == null` → тот же контроль. Пути >MAX_PATH Shell не поддерживает → `NoTrash` до старта. Экспериментальный быстрый путь `$Recycle.Bin` — «Решения для владельца» №5. |
| macOS | `trash` с методом `NsFileManager` (`trashItemAtURL`, одна операция rename на элемент, поддерживает Put Back). Элементы параллельно, 4 потока. |
| Linux | `trash` (FreeDesktop: `$XDG_DATA_HOME/Trash` или `$topdir/.Trash-$uid`, rename + `.trashinfo`). Нет корзины на томе → `NoTrash`. |

### 4.8 Сетевая копия (SMB/NFS)

- Windows: `CopyFile2` (без `COPY_FILE_NO_OFFLOAD`). Если src и dst на одном сервере, работает серверный copychunk, на SAN — ODX. Параллельно 8 файлов (латентность, а не канал, ограничивает мелкие файлы). `COPY_FILE_REQUEST_COMPRESSED_TRAFFIC` — опция `[ops] smb_compress` (выкл).
- macOS: `copyfile(COPYFILE_ALL)` по путям (smbfs сам использует серверное копирование, где умеет — проверяется бенчем S5-17).
- Linux: `copy_file_range` (cifs → copychunk, NFS 4.2 → server-side copy).
- Verify=Hash по сети: свой Stream-движок (данные и так идут через клиента), иначе readback удвоил бы трафик.
- Транзиентные ошибки (`ERROR_UNEXP_NET_ERR`, `ERROR_NETNAME_DELETED`, `ETIMEDOUT`, `EAGAIN`) повторяются автоматически: 3 раза с паузами 0,2/1/4 с, затем Issue.

### 4.9 Проверка копии

- `Verify::Hash`: хэш источника (xxh3-128 по умолчанию, blake3 — feature) считается на лету в Stream-движке. После commit файла пул верификации (2 потока) перечитывает dst без кэша (Windows `FILE_FLAG_NO_BUFFERING`, macOS `F_NOCACHE`, Linux `O_DIRECT` с выровненным буфером, при EINVAL — `fadvise(DONTNEED)` + обычное чтение) и сравнивает.
- Итог: 1 чтение src + 1 запись + 1 чтение dst вместо 2+1+2. Readback идёт параллельно со следующими файлами.
- Несовпадение → `Io(Other)` «контрольная сумма не совпала» с вариантами Повторить/Пропустить. Для Move источник не удаляется.
- Clone/rename не верифицируются (данные те же), в отчёте помечаются `cloned`.

### 4.10 Preallocate

Для файлов ≥1 МиБ:
- Windows — `FileAllocationInfo` (не EOF, иначе дорогое обнуление `ValidDataLength`);
- macOS — `F_PREALLOCATE`;
- Linux — `fallocate(mode 0)`.

`ENOSPC` на этом шаге → Issue `LowSpace` до записи данных.

### 4.11 Длинные пути и имена

- Windows: внутри `ops` только `\\?\C:\…` и `\\?\UNC\srv\share\…`. Нормализация (`.`, `..`, `/`) своя, до префикса. Глубокие деревья открываются относительно handle (`RootDirectory`), полный путь не собирается. Поддерживаются имена с хвостовыми точками и пробелами, `CON`/`NUL`.
- `names.rs` проверяет имя на ФС назначения ещё в планировщике:
  - FAT/exFAT/NTFS: запрещённые `<>:"/\|?*` и управляющие символы;
  - зарезервированные имена Windows;
  - длина компонента 255;
  - коллизии регистра (на нечувствительной ФС — ключ case-fold, на Windows — `CompareStringOrdinal(ignoreCase)`);
  - коллизии нормализации (APFS/HFS+ — NFC-ключ).
  Нарушение → `InvalidName` до копирования.

### 4.12 Свободное место

- Источники:
  - Windows — `GetDiskFreeSpaceExW` (lpFreeBytesAvailableToCaller, учитывает квоты);
  - macOS — `NSURLVolumeAvailableCapacityForImportantUsageKey` (учитывает purgeable), fallback `statfs`;
  - Linux — `statvfs` (`f_bavail*f_frsize`).
- Проверки:
  - заранее — по известному объёму;
  - по ходу — каждые 1 ГиБ записи: `free < remaining_known + max(1%, 256 МиБ)` → job паркует новые файлы с `LowSpace`, текущие дописываются.
- FAT32 и файл ≥4 ГиБ → `TooLarge` в планировщике.
- Clone, rename и move на том же томе место не проверяют.

### 4.13 Сравнение и синхронизация каталогов

- Quick:
  - параллельный обход обеих сторон (§3.4), merge по имени (ключ по правилам ФС dst);
  - равенство: size и `|mtime_a − mtime_b| ≤ max(time_res_a, time_res_b)` (FAT — 2 с, exFAT — 10 мс);
  - DST/таймзона на FAT: допуск ±1 ч опцией.
- Content:
  - сначала Quick;
  - для пар с равным size — параллельный xxh3 (rayon `spawn_cpu`, чтение на ops-воркерах): сначала первые 64 КиБ, затем полностью.
- Результат: `CompareResult { only_left, only_right, newer_left, newer_right, differs, equal }` в ext-состоянии ops (запрос 4). S2 подсвечивает его в панелях, Far-стиль выделяет различия.
- Sync: из результата строится план (`lr` = зеркало с удалением лишнего — только с явным флагом `delete_extra`; `both` = новый побеждает, конфликт обеих изменённых → Issue). План показывается превью (не модально), затем `apply` исполняет его как обычные copy/delete job.

### 4.14 Прочие операции

- **mkdir:**
  - `create_dir_all` своими вызовами (`CreateDirectoryW`/`mkdirat`);
  - `;` разделяет несколько имён;
  - после создания курсор ставится на первый созданный (`panel.cursor.to`).
- **rename:**
  - один элемент — как move на том же томе;
  - смена регистра — прямой вызов.
- **multi-rename:**
  - шаблон в стиле TC/Far: `[N]`, `[N2-5]`, `[E]`, `[C:start:step:width]`, `[Y][M][D]`, `[U]/[L]`, плюс regex-замена;
  - план `Vec<(from,to)>` строится в cpu-pool;
  - проверки: дубли в целевом наборе, существующие имена, недопустимые имена;
  - одно переименование на элемент (S0 №93): цепочка (a→b, b→c) — с хвоста, цикл (a→b, b→a) — через одно временное `.fnv~mr…` на цикл; сбой или отмена внутри цикла — откат цикла;
  - превью показывается до apply;
  - журнал хранит план для отката (`ops.multi_rename.undo` — фаза 2).
- **attrs/time:**
  - Windows: `SetFileInformationByHandle(FileBasicInfo)`;
  - macOS: `fchflags`/`setattrlist`;
  - Linux: `utimensat`/`fchmod`;
  - рекурсивно — через конвейер §3.
- **link:**
  - hard — `CreateHardLinkW`/`linkat`;
  - sym — `CreateSymbolicLinkW` с `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE`; при `ERROR_PRIVILEGE_NOT_HELD` → Issue с предложением junction для каталога;
  - junction — `FSCTL_SET_REPARSE_POINT` (mount point);
  - unix — `symlinkat`.
- **Ссылки при копировании** (`LinkMode::Preserve`): копируется сама ссылка.
  - Windows — `COPY_FILE_COPY_SYMLINK` или свой `CreateSymbolicLinkW` с той же целью;
  - junction — с той же абсолютной целью; если цель внутри копируемого дерева, она переписывается на новое место.
- **Облачные плейсхолдеры:**
  - Windows `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`/`OFFLINE`, macOS `SF_DATALESS`;
  - copy → Issue `Cloud` один раз на job («N файлов будут скачаны»), дальше по `CloudPolicy`;
  - move на том же томе и delete без скачивания.

## 5. Немодальные конфликты

1. **Обнаружение:**
   - до данных: при входе в существовавший каталог назначения worker берёт из `DestIndex` (один листинг на каталог, ключ — по правилам ФС dst) существующие имена;
   - финальная гарантия: create с `CREATE_NEW`/`O_EXCL` и rename с `NOREPLACE`. Гонка → Issue с `temp` (данные уже скопированы, решение «Заменить» = мгновенный rename с replace).
2. **Применение решения:**
   - per-job таблица `decided: HashMap<IssueKey, Resolution>`, где ключ — `IssueKind`, а для `Io` — `IoClass`;
   - есть ответ «для всех» или политика из `OpOptions` ≠ Ask → решение применяется сразу, без парковки.
3. **Парковка:**
   - `ParkQueue` (VecDeque, без лимита; элемент ≈200 Б) — элемент паркуется, worker идёт дальше;
   - `pending` родителя не уменьшается, поэтому каталог не финализируется и при Move не удаляется;
   - `Progress.parked += 1`.
4. **Вопросы:**
   - координатор в цикле берёт первый Issue, строит `PromptSpec` (`anchor: JobBar` или панель назначения, `allow_all: true`, тело «Конфликт 3 из 37: report.xlsx — новее, больше на 2,1 МБ»), вызывает `handle.ask()`. Ждёт только координатор, воркеры работают дальше;
   - ответ с `all` записывается в `decided` и применяется ко всем запаркованным того же ключа, без новых вопросов;
   - разобранные элементы ставятся в отдельную priority-очередь воркеров.
5. **Пакетный разбор:**
   - `ops.issues {job}` открывает список проблем job (ext-состояние, запрос 4);
   - S2 рисует его в панели как виртуальный листинг: мультивыбор и действие Заменить/Пропустить/Переименовать на выбранные.
6. **Конец работы:**
   - очередь работ пуста, а парковка нет → воркеры завершаются, job остаётся `Waiting`, потоков 0, кроме координатора;
   - ответ → воркеры поднимаются заново.
7. **Отмена job:**
   - в temp: удалить;
   - в Report: «не обработано N».

## 6. Атомарность, восстановление, persist-лог

### 6.1 Commit файла

| Случай | Порядок |
|---|---|
| новый файл < `small_file` | create(EXCL) под финальным именем → данные → metadata → **mtime последним** → close |
| новый ≥ `small_file` или любая перезапись | create temp `.<name>.fnv~<job36>` (Windows: +HIDDEN) в том же каталоге → данные → metadata → mtime → rename в финальное имя (Windows: `FileRenameInfoEx` на открытом handle — без повторного открытия; unix: `renameat2`/`renamex_np`; Overwrite → с заменой, атомарно для читателей) |
| `Durability::Safe` | + fsync данных перед mtime; + fsync каталога после rename (unix) |
| `RenameExisting` | `old → old.bak~N` (NOREPLACE), затем commit нового |

### 6.2 Журнал

- Файл: `state_dir/jobs/<job-uuid>.jnl`, блокировка `File::try_lock` на время жизни job.
- Формат: `[u32 len][u32 crc32][postcard Record]`, append-only.

```rust
enum Record {
    Header { v: u16, req: OpRequest, started: i64, pid: u32 },   // fsync
    Phase(Phase),
    Counters { items: u64, bytes: u64 },                         // каждые 5 с
    Root(PathBuf),                                               // корень назначения (для чистки temp)
    Temp(PathBuf),                                               // перед созданием temp (только ≥ small_file)
    TempDone(PathBuf),
    Done { summary: JobSummary },                                // fsync, затем файл удаляется
}
```

- Буфер `BufWriter`, flush раз в 1 с с отдельной полосы (не из воркеров).
- Стоимость: ≈ две записи на крупный файл, ноль на мелкий.

### 6.3 Восстановление

При старте (`register`, задача на Lane::Bulk):
1. Сканируется `jobs/*.jnl`. Файл захватывается `try_lock`: занят — это живой второй экземпляр, пропускаем.
2. Читаются записи до первой битой (crc). Есть `Done` → файл удаляется.
3. Иначе показывается баннер: «Прервано: копирование 12 480 файлов → D:\Backup (выполнено ≈63%). [Продолжить] [Очистить]» (запрос 9).
4. **Продолжить:** удалить `Temp` без `TempDone`, затем повторить `req` с `conflict = SkipIdentical` для Copy/Move. Файлы с mtime≠src или другим size повторно копируются, без вопросов, если они в списке `Root`, — это наши недописанные. Delete/Trash просто повторяются.
5. **Очистить:** удалить temp, удалить журнал.

Move после падения консистентен: источник удаляется только после commit копии.

### 6.4 Выход с активными задачами

`app.quit` при активных ops-job → inline-вопрос «Идут операции (2). [Дождаться] [Прервать и выйти] [Свернуть в фон — фаза 2]» (запрос 7). «Прервать» → cancel, temp удаляются, журнал остаётся для «Продолжить».

## 7. План бенчей и целевые цифры

**Датасеты** (генерирует S9, сиды фиксированы):
- B1 — 1 × 20 ГиБ;
- B2 — 100k × 1–64 КиБ, глубина 6 (node_modules-подобный);
- B3 — смешанный 10 ГиБ / 50k (код + медиа);
- B4 — 10k файлов с путями 300–1000 символов;
- B5 — sparse-образ 50 ГиБ (данных 5 ГиБ);
- B6 — 1k × 100 МиБ.

**Стенд:**
- Windows: NVMe (NTFS и Dev Drive ReFS), внешний USB-SSD, HDD (USB), SMB 1 GbE;
- macOS: внутренний APFS, внешний SSD (APFS/exFAT);
- Linux: ext4, btrfs, xfs (VMware).

**Метод:**
- `bench_ops` (игнорируемый тест `urfin-ops`, S5-25), 5 прогонов, медиана и p95;
- холодный кэш перед прогоном: Windows — `RAMMap -Et`, macOS — `purge`, Linux — `drop_caches`;
- Defender: штатный режим и режим Dev Drive performance — фиксировать оба.

**Конкуренты:**
- Explorer — скрипт через `IFileOperation` (тот же движок, что Explorer, автоматизируемо) плюс 1 ручной контроль секундомером;
- Finder — AppleScript `duplicate`/`move`/`delete`;
- robocopy `/E /MT:16 /NFL /NDL /NP /R:0`, для крупных `/J`;
- FAR 3 x64 — ручной прогон ×3 (время из лога Far);
- Linux — `cp -r --reflink=auto`, `rsync -a`.

Метрики:
- время до конца;
- **время до первого байта** (TTFB);
- CPU;
- пиковая RSS ops (<100 МиБ на 1M файлов).

- Цель: прямой перенос в `\$Recycle.Bin\<SID>\$R…` + запись `$I`-файла (v2), уведомление Shell (`SHChangeNotify`), feature-флаг `experimental_fast_trash`.
- Приёмка:
  - Explorer видит элементы и восстанавливает их;
  - бенч #10 ≥10×.
- Зависит: 13, «Решения для владельца» №5.

**S5-27 Докачка крупных файлов (фаза 2)**
- Цель: для файлов ≥1 ГиБ на Net/USB журнал хранит подтверждённый offset (fsync каждые 256 МиБ), «Продолжить» дописывает.
- Зависит: 12, 16.

Порядок: 01 → (02 ∥ 03) → 04 → 05 → 06 → 07 → (08 ∥ 09 ∥ 10) → 11 → 12 ⇒ **MVP**. Затем 25 (база) → 14 → (15 ∥ 16 ∥ 17 ∥ 18) → 19 → 20 → 21 → 13 → 22 → 23 → 24 → 26 → 27.

## 10. Запросы к S0

1. **Потоки ops.** Разрешить ops создавать собственные потоки через `Runtime::spawn_dedicated`: координатор и до `max_threads` воркеров на все job. Зафиксировать в S1, что `Lane::Bulk` предназначен только для коротких задач. Иначе долгая копия или `ask` займут оба Bulk-потока и остановят запись сессии.
2. **JobRegistry: очередь, приоритет, ретрай.**
   - `JobSpec { priority: u8, owner_ns: &'static str }`;
   - `JobHandle::set_state(Queued|Running)`, чтобы S5 держал job в очереди устройства;
   - роутинг `job.retry {id}` / `job.priority {id}` в handler `owner_ns`;
   - уточнить семантику `Waiting(PromptId)`: «есть открытый вопрос», при этом прогресс может идти. Переходы `Waiting↔Running` повторяемы.
3. **Progress.** Добавить `phase: AtomicU8` (Scan/Transfer/Verify/Finalize/Recover), `total_final: AtomicBool`, `parked: AtomicU32` и поля в `ProgressSnap`.
4. **Ext-состояние для UI.** Нужен механизм, через который крейт хранит своё читаемое UI состояние: список проблем job, превью multi-rename, результат compare. Предложение: `AppState.ext: Extensions` (типизированная map `get::<T>()`/`get_mut::<T>()`, `T: Any`), мутации только в handler/Msg.
5. **Списки в аргументах команд.** `Value::List(Arc<[Value]>)` (или `Value::Locs`), чтобы `ops.copy src=[…] dest=…` работал из cmdline и макросов, а не только по `Targets`.
6. **Владелец `VolumeInfo`.** Определение тома, носителя, ФС и возможностей нужно и S4 (индикатор места, case-правила сортировки), и S5. Предложение: модуль `urfin_vfs::volume` (S4 владеет API, S5 реализует sys-часть в задаче S5-02).
7. **Выход с активными задачами.** Хук `Handler::on_quit(&mut self, cx) -> QuitDecision { Allow, Veto(PromptSpec) }` вызывается в `app.quit` до `shutdown(200 ms)`.
8. **Коалесцирование `panel.refresh`.** Core дедуплицирует `panel.refresh` по tab в пределах pump. S4-watcher коалесцирует события ≥100 мс и подавляется для каталогов, о которых ops сообщает сам (`ops` шлёт refresh ≤1/с на таб).
9. **Banner с несколькими действиями.** `Banner.actions: SmallVec<[(CompactString, Command); 3]>` вместо одного `action` (Продолжить / Очистить).
10. **Структурированное тело prompt.** `PromptSpec.detail: Option<PromptDetail>`, где `PromptDetail::Conflict { src: Entry, dst: Entry, index: u32, total: u32 }`, чтобы S2 рисовал сравнение двух файлов (размер, дата, «новее»), а не строку.
11. **Датасеты S9.** B1–B6 из §7 с фиксированными сидами, генератор офлайн, `xtask gen-dataset`.

## 11. Решения для владельца

1. **Удаление по умолчанию: корзина или насовсем.** Удаление в корзину медленнее, и на сетевых томах корзины нет. Удаление насовсем — риск потери данных.
   - Варианты:
     - (а) F8/Del → корзина, Shift → насовсем (как Explorer/Finder);
     - (б) F8 → насовсем (как классический DN/Far без настройки);
     - (в) спрашивать inline каждый раз.
   - Рекомендация: **(а)**, плюс inline-подтверждение одной строкой (Enter). Элементы, которые нельзя в корзину, дают отдельный вопрос, тихо насовсем не удаляются.
2. **Верификация копий по умолчанию.** Хэш с readback стоит около +30–60% времени.
   - Варианты:
     - (а) выкл всегда;
     - (б) выкл для copy, Size+fsync для межтомного move;
     - (в) Hash всегда.
   - Рекомендация: **(б)**. Hash включается флагом в строке операции или в конфиге. Для move межтомного это защита источника при цене ≈0.
3. **Какие метаданные сохранять.**
   - Варианты:
     - (а) как Explorer/Finder: данные, атрибуты, время, ADS/xattr (включая Mark-of-the-Web и quarantine), права наследуются в месте назначения;
     - (б) как robocopy /COPYALL: плюс ACL/владелец (нужны привилегии, на чужих ФС ошибки).
   - Рекомендация: **(а)** по умолчанию, (б) — опция «с правами» в строке операции.
4. **Возобновление после сбоя.**
   - Варианты:
     - (а) автоматически продолжать прерванные job при старте;
     - (б) баннер «Прервано… [Продолжить] [Очистить]»;
     - (в) молча чистить temp.
   - Рекомендация: **(б)**. Пользователь видит, что произошло, и автоматическая запись на диск после краша не начинается сама.
5. **Быстрая корзина Windows через прямую запись в `$Recycle.Bin`.** Формат `$I` недокументирован, но стабилен с Windows 10. Даёт ≥10× на больших папках, риск — несовместимость в будущих версиях Windows.
   - Варианты:
     - (а) не делать;
     - (б) за флагом, выкл по умолчанию;
     - (в) по умолчанию с откатом на IFileOperation при ошибке.
   - Рекомендация: **(б)**, пересмотреть к релизу M6 по итогам бенчей и багов.
