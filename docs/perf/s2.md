# S2-20: кадр интерфейса и аллокации

Бюджет (S2-20, S0 2026-10-16): CPU UI-потока на кадр ≤ 2 мс (p99) при 100k строк; аллокации
стационарного кадра одинаковы для 1k и 100k. Спека писалась под egui (`ui.show`,
`tessellate`); под GPUI мерим то же целиком — время UI-потока между кадрами.

## Как меряем

`urfin.exe --bench <каталог>` (G-07, сценарий — `docs/perf/gpui-vs-egui.md`):

- `<фаза>_ui_p50/_ui_p99` — CPU UI-потока между соседними кадрами, мс: `QueryThreadCycleTime`
  и калибровка циклов по часам (30 мс занятого цикла); `GetThreadTimes` идёт тиками
  планировщика (~15,6 мс) и для одного кадра не годится. Сюда входит всё, что поток сделал за
  кадр: проход Core, `render`, раскладка и отрисовка GPUI.
- `<фаза>_allocs_p50/_allocs_max` — аллокации между кадрами: только сборка
  `--features count-alloc` (счётчик в глобальном аллокаторе; в release-граф не попадает,
  `ci/release_features.py`). Счёт аллокаций от профиля не зависит — меряем на dev-сборке.

Датасеты: `cargo run -p urfin-testdata --example gen_tree --release -- --n 100000 --seed 1`
(и `--n 1000`).

## Базовая линия (2026-10-26, до оптимизации)

Стенд владельца, release, `gen-100000-s1`, 3 прогона, медианы; окно бенча на втором экране без
фокуса, машина под обычной нагрузкой.

| Фаза | интервал p50 / p99, мс | UI-поток на кадр p50 / p99, мс | `render` p50, мс |
|---|---:|---:|---:|
| Листание (3 строки за кадр) | 6,95 / 8,39 | **2,92 / 4,30** | 0,18 |
| PgDn каждый кадр | 6,94 / 8,11 | **3,41 / 4,79** | 0,16 |
| Ресайз (программный) | 12,76 / 21,62 | 6,16 / 10,41 | 0,10 |
| Терминал 200×60, полная пересборка | 7,01 / 11,13 | 6,42 / 10,05 | 2,61 |

Простой — 0 кадров, 0 % CPU. Память: пик рабочего набора 151 МБ, private 131 МБ. Бинарь 26,96 МиБ.

Аллокации между кадрами (dev, `count-alloc`), p50:

| Фаза | 1k | 100k |
|---|---:|---:|
| Листание | 1 629 | 1 829 |
| PgDn | 1 190 | 1 953 |
| Ресайз | 3 101 | 3 336 |
| Терминал | 4 866 | 4 494 |

На 1k листание и PgDn быстро упираются в конец списка, и кадр перестаёт меняться, — сравнение
«стационарного кадра» требует сценария с одинаковой сменой видимых строк (следующий шаг).

## Шаг 2 (2026-10-29): низ окна тремя view, стационарный кадр

Профиль (`URFIN_PROF`, теперь ещё `<файл>.folded` — свёрнутые стеки для разбора по вызывающим):
треть кадра — раскладка taffy и запрос раскладки; низ окна (cmdline + статус + F-клавиши) был одной
кэшируемой view, а статус-строка меняется на каждом шаге курсора — каждый кадр пересобирались и
раскладывались все F-клавиши. Теперь cmdline, статус и F-клавиши — три view со своими отпечатками
(`chrome::Bottom`). Новая фаза бенча `steady` — курсор ходит по 10 строкам вниз и обратно без
прокрутки: кадр одинаков на любом каталоге.

Release (thin LTO, с символами), `gen-100000-s1`, 3 прогона; UI-поток на кадр p50 / p99, мс:

| Фаза | до | после |
|---|---:|---:|
| Листание | 2,92 / 4,30 | **2,41–2,65 / 3,64–4,05** |
| PgDn | 3,41 / 4,79 | 3,20–3,33 / 4,74–5,01 |
| Стационарный кадр | — | 2,27–2,38 / 3,54–3,97 |
| Ресайз | 6,16 / 10,41 | 4,81–5,25 / 7,71–10,68 |

`gen-1000-s1`: листание 2,68 / 4,36, стационарный 2,36 / 3,83 — как на 100k.

Аллокации стационарного кадра (dev, `count-alloc`), p50 / max: 1k — 1331 / 1340, 100k — 990 / 999.
От числа файлов не растут; разница — содержимое первой страницы (имена, обрезка «…»).

Что осталось в кадре (профиль, доли от `Window::draw`): `Scene::finish` (сортировка спрайтов) 12 %,
отрисовка глифов и `BoundsTree` 18 %, шейпинг новых строк DirectWrite 17 %, раскладка taffy
заголовка и табов 9 %. Это цена кадра gpui на каждый видимый глиф: даже стационарный кадр (ни
одного нового имени) стоит ~2,3 мс. Бюджет 2 мс p99 писался под egui — без правок gpui
недостижим.

## Итог и дальше

- Бюджет 2 мс не выполнен: p99 листания 4,3 мс, PgDn 4,8 мс. Сборка дерева в `render` — 0,2 мс;
  основное — раскладка, шейпинг новых имён (DirectWrite) и отрисовка GPUI, проход Core.
- Аллокаций на кадр 1–3 тыс., почти все — GPUI; от числа строк каталога зависят слабо.
- Следующий шаг S2-20: профиль UI-потока (`URFIN_PROF`) на листании, кэш шейпинга строк,
  сценарий стационарного кадра для сравнения 1k/100k, порог в CI.
