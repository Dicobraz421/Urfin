# ADR-0024: точная подсветка видимого окна для файлов любого размера

Статус: **принято** ([решение владельца 2026-11-02](../decisions/2026-11-02-windowed-highlight.md)), класс A — межкрейтовый контракт (`docs/CONTRACTS.md`) не меняется. Заменяет ADR-0023 §7 и ответ 4 «Решено владельцем 2026-11-01» в части подсветки и свёртки; S7 §5.7 — по этому ADR. Карточка — [S7-41](../tasks/S7-41.md).

## Контекст

- S7-21 (#253): вьювер разбирал tree-sitter'ом весь файл ≤ 16 МиБ; S7-35 (#266): редактор — тоже весь файл ≤ 16 МиБ, с прежним деревом. Замер S7-35 (`docs/perf/s7.md`): на 16 МиБ цвета после правки — JSON 0,16–0,23 с, TOML 1,3–2,9 с, дерево — 0,6–0,8 ГБ памяти. Бюджеты (ADR-0023 §6, решение 2026-10-29): ≤ 64 МиБ на документ, цвета после правки ≤ 50 мс, кадр p99 ≤ 6 мс.
- Владелец 2026-11-02: подсветка — «как сам редактор: только видимый кусок», для файлов **любого размера**, «никаких неточностей» — в том числе для структуры на много экранов и строк/комментариев, начавшихся далеко выше экрана.
- Цвет байта зависит от всего текста выше (открытая кавычка, комментарий, ключ или значение JSON по стеку скобок). Поэтому «только окно» без знания состояния на его начале неточно; знание состояния — проход по файлу, но проход лёгкий (лексика, не дерево) и хранит только контрольные точки.

## Решение

### 1. Один источник истины на язык, для любого размера

| Языки | Чем красится окно | Почему так |
|---|---|---|
| JSON, TOML, INI, XML | **Свой возобновляемый лексер** (`view/src/syntax/lex/`) | Роль токена определяется лексикой и стеком скобок; внутри одного значения JSON на 10 ГБ нет места, с которого tree-sitter можно начать |
| YAML, Markdown | **tree-sitter + свой `highlights.scm`** по отрезку `[S, E)` вокруг окна | Грамматики сложные (сканер YAML — 1,4 тыс. строк), зато у них есть строки, с которых разбор начинается заново без потери точности (п. 3) |
| Пакетные: LANGS_ON | **Трекер состояния + tree-sitter по кускам** между границами трекера (п. 8) | Роли зависят от дерева (вызов, тип, объявление), свой разбор их не повторит; зато у кода есть границы элементов, а лексика и вложенность считаются лёгким автоматом |
| Пакетные: LANGS_OFF | Как раньше: полный разбор ≤ 16 МиБ (`MARKUP_MAX`), больше — без подсветки | Границы не доказаны (п. 8, «Не перенесены») |

Малые и большие файлы идут одним путём: цвета не зависят от размера.

### 2. Контрольные точки (`syntax::marks`)

- Фоновый проход по всему файлу (вьювер — `ByteSource`, редактор — снимок `TextSnap`) кусками по 1 МиБ, без загрузки файла в память. Не-UTF-8 — перекодирование куска в UTF-8 с картой смещений (`search::transcode`, как поиск), BOM пропускается; ISO-2022-JP (состояние декодера между кусками) — без подсветки.
- Точка — не реже чем через 64 КиБ, в месте, где состояние лексера полно (не внутри короткого токена): смещение (байт источника), состояние `St` (16 байт: режим языка и роли контейнеров верхних 64 уровней стека битами), глубина вложенности на точке и минимум глубины на куске до следующей точки. 10 ГБ → ≈ 160 тыс. точек ≈ 6 МБ.
- Глубже 64 уровней стек не хранится: роль уровня `j` восстанавливается по сводкам — последний кусок, где глубина опускалась ниже `j`, проходится заново (≤ 64 КиБ). Так у патологической вложенности (`[[[[…` на гигабайт) память не растёт.
- YAML и Markdown — свой лёгкий построчный трекер вместо лексера: состояние на точке — многострочная конструкция, в которой стоит начало строки (ограждённый код, HTML-блок 1–5; кавычки, поток `[`/`{`, блочный скаляр).

### 3. Окно

- Окно — видимые байты ± 64 КиБ (как S7-35). Лексер: от ближайшей точки ≤ начала окна до конца окна; итог — отрезки ролей (`Span`, смещения `u64`), места свёртки, «инертные зоны» (п. 4).
- **Markdown**: `S` — ближайшая «безопасная» строка ≤ начала окна, `E` — первая ≥ конца; каждый кусок `[S, E)` между соседними безопасными строками — свой разбор (§6 п. 4). Безопасная строка — с колонки 0, вне ограждённого кода и HTML-блока, и: после пустой строки (кроме `---`/`+++` — метаданные), или заголовок ATX, или пункт маркированного списка, или `1.`/`1)`. Такая строка закрывает все контейнеры и абзац выше, а начатое ею не зависит от текста выше.
- **Метаданные Markdown** (`---`/`+++` в первой строке) — только если закрыты в первых 64 КиБ текста; это решается до первой строки, по первым 64 КиБ (`Lex::begin`). Без закрытия текст — обычный Markdown со своими безопасными строками: `---` там разрыв, окно разбирает только свои куски (раньше весь файл был одним куском на каждое окно).
- **YAML**: `S` — строка ключа или элемента списка (`- `) вне многострочного, `---`, или начало файла; отрезок `S` — до первой содержательной строки с меньшим отступом, с тем же отступом другого вида или маркера документа; разрез `E` — следующая за концом окна строка того же отступа и вида. Отрезки идут подряд, пока не покроют окно; каждый — отдельный разбор.
- Разбор `[S, E)` — тот же запрос `highlights.scm`; Markdown — строчная грамматика **по каждому узлу `inline`/ячейке таблицы отдельно** (как `MarkdownParser` крейта `tree-sitter-md`). Прежний код разбирал все абзацы одним строчным документом — код и ссылки «перетекали» между абзацами; это исправлено и для полного разбора.

### 4. Правка (редактор) и «без неточных цветов»

- Точки до правки верны; после — сдвигаются и «под вопросом». Пересчёт — от точки перед правкой вперёд, пока состояние не совпадёт со старой (сдвинутой) точкой: тогда все точки за ней снова верны (глубина хранится разностями — лишняя скобка их не портит). Обычно это один кусок (≈ 0,1 мс). Не совпало (открыли кавычку или скобку) — проход идёт до конца файла в фоне, а окно считается сразу от точки перед правкой: для него точки за правкой не нужны.
- На экране только гарантированно верное:
  - **правка внутри инертной зоны** (внутренность строки или комментария, где вставленные/удалённые байты — не кавычка, не `\`, не перевод строки и не символы конца комментария) — цвета сдвигаются: состояние лексера после зоны доказуемо то же;
  - **иначе** — отрезки до начала строки правки остаются (лексер — слева направо, роль токена задаёт его начало), YAML — до начала отрезка `S`, Markdown — до безопасной строки; от этого места до конца окна — без цвета, пока не придёт окно (единицы мс, кадр-два).
- Первая строка Markdown зависит от текста ниже (закрыты ли метаданные), поэтому правка в первых 64 КиБ пересчитывает точки с начала (`Lang::head`), а у текста с незакрытой оградой строки в этих 64 КиБ не якоря: правка может её закрыть, и цвета выше станут метаданными.
- Вьювер: окно вне посчитанного — без цвета до ответа; если проход ещё не дошёл до окна (10 ГБ, прыжок в конец), окно ждёт прохода (без цвета), состояние «Подсветка N %» видно в статусе.

### 5. Свёртка — из тех же событий структуры

Лексер и трекер выдают «открыть»/«закрыть»: скобки JSON и TOML, таблица TOML (до следующего заголовка), элемент XML, многострочные комментарий, строка, CDATA; YAML — уровень отступа строки ключа или элемента; Markdown — раздел заголовка ATX (до заголовка того же или старшего уровня), ограждённый код, пункт списка любого уровня, список верхнего уровня целиком и цитата `>` (контейнеры CommonMark, решение [2026-11-03](../decisions/2026-11-03-highlight-edge-cases.md)). Место свёртки строки — первое открытие на ней, закрытие которого на другой строке; закрывающая строка видна, если закрытие стоит первым на ней (`}`, `</a>`, следующая таблица, закрывающая ограда), пустые строки в конце скрытого видны. Закрытие далеко ниже окна ищется по сводкам минимума глубины (без чтения файла) и проходом одного куска. Правило одно для всех размеров. Пакетные языки с трекером (п. 8) — те же события: скобки, `#if`, многострочные комментарий и строка, блок Python по отступу; без дерева свёртка не отличает узел от скобки, поэтому сворачивается и многострочный вызов, а заголовок `if` на двух строках — со строки скобки. Пакетные без трекера — прежняя свёртка по дереву.

### 6. Гарантия точности

Дифференциальные тесты (`syntax/lex/*_tests.rs`, `syntax/marks_tests.rs`; в CI — файлы репозитория и генераторы, внешний корпус — `HL_CORPUS=… --run-ignored only`):
1. **Лексер = tree-sitter + `highlights.scm`** для JSON, TOML, INI, XML: файлы репозитория, генераторы proptest корректных документов, случайные цепочки токенов (сравниваются только разобранные tree-sitter без `ERROR`/`MISSING`). Сравнение — роль каждого непробельного байта: пробел, табуляция и перевод строки цвета на экране не имеют. Внешний корпус (`~/.cargo/registry`, 2026-11-02): JSON — 3135 файлов, TOML — 2002, XML (и `.svg`, `.xsd`…) — 2255, расхождений 0. INI — только генераторы (файлов в корпусе нет).
2. **Отрезок = полный разбор** для YAML и Markdown: окна по строкам и случайные окна совпадают с полным разбором (внешний корпус — 3497 файлов Markdown и YAML, расхождений 0).
3. **Окно с любой точки = проход с начала** (все языки, и на неверных документах); **точки после случайных правок = проход с нуля** (состояние и глубина на каждой точке); вложенность 300 и 70 000 уровней (глубже памяти прохода) = проход без точек.
4. **Ошибки оракула** — где верна спецификация, а не грамматика: сканер `tree-sitter-xml` не закрывает CDATA на `]]]>` и не закрывает пустую `<![CDATA[]]>` (тянет строку до следующего `]]>` в файле); лексер закрывает на первом `]]>`, такие документы из сравнения исключены (`testkit::oracle_bug`, решение [2026-11-03](../decisions/2026-11-03-highlight-edge-cases.md)). Сканер `tree-sitter-md` расходится с `CommonMark` в HTML-блоках (`<textarea`, `<!x` строчной, `<?>`, конец типа 4): красим по спецификации, а цвет от положения окна не зависит **ни на каком входе**, потому что устроено так:
   - **Модель.** Текст делится на куски по безопасным строкам — они зависят только от текста выше (трекер, точки). Каждый кусок — **свой разбор** tree-sitter, и роли куска — функция только его байтов. Окно разбирает те же куски, что и проход с начала, поэтому равенство «окно = проход с начала» держится по построению: ни от согласия грамматики со спецификацией, ни от её восстановления после ошибки оно не зависит.
   - **HTML-блоки определяет трекер** — по `CommonMark`, на любом уровне контейнеров (`lex/md/nest.rs`, `Out::html`): конец блока — по его типу или с контейнером. Безопасная строка в блок не попадает.
   - **Грамматика блоков не видит**: она получает копию куска, где строка блока от столбца содержимого контейнеров заменена пустым заголовком `#` той же длины (`win::mask_html`). Заголовок, как и строка HTML-блока, — блок в одну строку: контейнеры те же, абзац прерван, на следующую строку ничего не переходит; смещения не меняются. Узел маски красится ролью `html_block` (с продолжением контейнера на следующей строке, как у настоящего блока), `>` внутри блока — той же ролью (`Out::html_quote`).
   - **Метаданные** — свойство начала текста (§3), а не потока: незакрытая ограда кусков не склеивает, равенство «окно = проход с начала» держится той же моделью. Файл 16 МиБ с незакрытой оградой: окно читает ≈ 140 КиБ, не весь файл.
   - **Определения ссылок**: абзац из одних определений заголовком Setext не становится (`===` под ним — текст абзаца, `<a>` за ним HTML-блока не начинает); разбор определений в несколько строк — автомат по строкам абзаца (`lex/md/refdef.rs`), его состояние — в точке. Грамматика такое подчёркивание считает заголовком, поэтому видит его маской той же длины (`win::mask_setext`): текст — буквами, разрыв — `***`; сравнение с tree-sitter такие тексты пропускает (`testkit::md_setext_agrees`).
   - **Тесты** (`lex/md/zone_tests.rs`): окно с любой точки = проход с начала — на генераторе, который нацелен на расхождения, и на произвольных байтах, без фильтра `md_html_agrees`; зоны трекера = `CommonMark` (эталон — pulldown-cmark). Сравнение с tree-sitter (п. 2) осталось только там, где он согласен со спецификацией (`testkit::md_html_agrees`).
5. Неверный документ (ошибка синтаксиса): у лексера — свои локальные правила (описаны в модулях: незакрытая строка JSON кончается на переводе строки, как токен tree-sitter; `1e+5` — число, хотя грамматика tree-sitter-json знака в порядке не знает, и т. п.); у YAML/Markdown — восстановление tree-sitter в пределах отрезка. Полный разбор tree-sitter на неверном документе «истиной» не считается: его восстановление после ошибки зависит от всего файла (ошибка в начале красит конец).

### 7. Бюджеты и потоки

- Память на документ: точки ≈ 0,6 МБ на ГБ (10 ГБ — 6 МБ) + окно; дерево tree-sitter — только отрезка окна. В потолке ADR-0023 §6 (64 МиБ).
- Цвета после правки ≤ 50 мс (лексер — десятки мкс на окно, tree-sitter отрезка — единицы мс), кадр p99 ≤ 6 мс: UI-поток только сдвигает и рисует готовые отрезки; проход, окно и разбор — `Lane::Interactive` (окно) и `Lane::Bulk` (проход по файлу).
- Имена tracing-спанов — `view.syntax.*` (пространство `view.*` контракта).

### 8. Пакетные языки: трекер и куски

Цвет байта у языков-пакетов задаёт дерево, а дерево — весь текст выше. Но код — это списки элементов (оператор, член класса, элемент массива), и элемент разбирается одинаково, какие бы соседи ни стояли рядом. Отсюда подход (`syntax/lex/code.rs`, `lex/code/*.rs`, `syntax/cutwin.rs`):

1. **Трекер** — лёгкий автомат без дерева (сотни МБ/с), состояние — на точках (п. 2): режим лексики (строка, комментарий, raw-строка, шаблон и f-строка с вложенными выражениями, регулярка, директива, JSX) и стек уровней до 32 (`(`, `[`, `{` тела, списка, ветвей, типа; `#if`; блок Python по отступу). Закрывающая скобка без пары глубину не меняет, `}` снимает незакрытые `(` и `[`, `#else`/`#endif` — незакрытое внутри ветви.
2. **Кандидат** — начало строки (только пробелы до токена), на которой начинается новый элемент своего уровня: прошлый токен кончил элемент (`;`, `}` тела, запятая в списке; Go — автоточка с запятой по спецификации; JS — ключевое слово оператора после значения; Python — новая логическая строка), а первый токен строки продолжить его не может (не `else`, `catch`, `while`, `where`, не закрывающая скобка, в `switch`/`select` — только `case`/`default`; Rust в `match` — не охрана `if`). Комментарии над строкой остаются в куске выше.
3. **Граница** (`Out::cut`) — кандидат не ближе 8 КиБ от прошлой границы. Расстояние до прошлой границы — в состоянии точки, поэтому набор границ — функция текста от его начала и не зависит от окна; кандидаты внутри длинного тела становятся границами так же, как и на верхнем уровне.
4. **Цепочка уровней.** Граница внутри уровня несёт его заголовок: текст от прошлого кандидата внешнего уровня до открывающей скобки — настоящий текст файла, не шаблон: вид блока определяет сама грамматика. Заголовок длиннее 4 КиБ, уровень глубже 32 или не список элементов — уровень «вне цепочки», внутри него границ нет. Кадры не хранятся: при окне они восстанавливаются сводками глубины (п. 2).
5. **Кусок** `[S, E)` — текст между соседними границами — разбирается как `заголовки S + текст + закрытия E`. Это верный документ, из которого выброшены соседние элементы всех уровней. Закрытия — скобки уровней на `E` и `;`, где конец заголовка не конец оператора (`let x = f(|| {` → `});`; `$(` Rust → `)*`; `#if` → `#endif`). Роли берутся только с текста куска. Кусок длиннее 16 МиБ не разбирается — цвета нет, как раньше у больших файлов.
6. **Почему совпадает с полным разбором.** Грамматика контекстно-свободна; элемент списка выводится из одних своих токенов, поэтому в документе без ошибок удаление соседних элементов оставляет его поддерево тем же — если разбор элемента не решается текстом за его пределами. Такие места — конечный список, каждое найдено сверкой и закрыто правилом трекера:
   - у грамматик C первый элемент уровня разбирается иначе, чем следующие (`STACK_OF(X) *p;`: GLR с динамическим приоритетом) — перед куском ставится пустышка `int _;`, у первого элемента текста границы нет;
   - JS: `({a, b}) =>` — образец или объект решает текст после скобки: запятая внутри круглых скобок не граница; `await (…)()` — вызов функции `await`: внутри такой скобки границ нет;
   - Rust: внутри образца и охраны ветви `match` (до `=>`) границ нет; `Foo { a }` с новой строки `if` — охрана этой ветви, не оператор;
   - Java: у `enum` список констант и члены — разные части: внутри него границ нет;
   - `#else`/`#elif`: ветвь идёт целиком; значение `#define` с пробелом за именем продолжается на следующих строках (как у грамматики).
7. **Гарантия — сверкой на всех кандидатах**: тесты ставят границу на **каждый** кандидат (`cut_min = 0`), то есть проверяют не 8-килобайтные куски, а каждое место, где кусок вообще может начаться; окно всего файла сравнивается с полным разбором по ролям непробельных байт (`lex/code/tests.rs`, пакеты — `HL_PACK=<папка DLL>`, внешний корпус — `HL_CORPUS`, в CI пакетов нет и сверка пропускается: идут тесты трекера). Числа — ниже.
8. **Текст с ошибкой.** Полный разбор на нём истиной не считается (п. 6, п. 5 и решение 2026-11-03): ошибка держится в своём куске. Цвета по-прежнему не зависят от окна: границы — функция текста, каждый кусок разбирается отдельно.
9. **Правка.** Точки — как в п. 4 (сходимость — ещё и при равной глубине: в состоянии номера уровней). Якоря — кандидаты: выше кандидата цвета от текста ниже не зависят по той же причине, что и у границы. Строка кандидата сама зависит от своего первого токена — поэтому берётся якорь на один раньше (как у YAML и Markdown).
10. **Без пакета** (DLL нет): вьювер не включает «Разметку» (`syntax_ok`), редактор узнаёт это в первой задаче и больше задач не ставит; трекер без грамматики работает, но не нужен.

## Отвергнуто

- **Полный разбор tree-sitter для малых, окна для больших** — два источника истины, цвета менялись бы на пороге; полный разбор на 16 МиБ и так вне бюджета (S7-35).
- **tree-sitter по окну без состояния** («разобрать видимое») — неточно: строка, комментарий, ключ/значение начинаются выше окна.
- **tree-sitter для JSON/TOML/XML по отрезкам** (с искусственным префиксом скобок) — внутри одного значения нет безопасной строки, а префикс — тот же лексер стека; свой лексер проще и в 100 раз быстрее.
- **Свои лексеры для YAML и Markdown** — грамматики с отступами, ленивыми продолжениями и setext-заголовками; повторить их точно дороже, чем найти безопасные строки (проверено на корпусе, п. 6).
- **Старые цвета, сдвинутые правкой, до нового окна** — могут быть неверны (открыли кавычку); показываются только там, где верны доказуемо (п. 4).
- **Свои лексеры для пакетных языков** (как JSON) — роль зависит от дерева: вызов функции, тип, объявление; `a * b;` в C — умножение или объявление. Повторить это значит написать разбор.
- **Отрезки только верхнего уровня** — один класс Java, `namespace` C#/C++, `mod` Rust, IIFE в JS — весь файл; нужна вложенность.
- **Шаблонный префикс вместо заголовка** (`class X {` по виду скобки) — вид блока лексика не знает (`new X() {` — тело класса, `if (a) {` — блок, оба после `)`); настоящий заголовок снимает вопрос.
- **Хранить кадры в точках** — смещения пришлось бы сдвигать при правках и сравнивать при сходимости; сводки глубины уже дают открытие уровня за проход одного куска.
- **Разбирать весь файл в фоне и выбрасывать дерево** — памяти на дерево 16 МиБ нужно 0,6 ГБ на время разбора, а 1 ГБ кода — десятки минут.

## Последствия

- Вьювер («Разметка», быстрый просмотр) и редактор красят JSON/TOML/INI/XML/YAML/Markdown и пакетные языки с трекером (п. 8) любого размера; порог 16 МиБ остаётся у непереведённых пакетных и у куска без границ.
- Свёртка встроенных языков — по своим правилам (п. 5): места те же для обычных документов, но у XML не сворачивается текст между тегами, у Markdown — списки и цитаты (только разделы и код).
- В Markdown строчные элементы больше не перетекают между абзацами (исправление ошибки).
- Новый язык в exe — лексер или трекер безопасных строк и дифференциальный тест; новый пакетный — трекер границ и сверка на всех кандидатах.
- Состояние точки выросло (стек уровней, расстояния, отступы Python): точки ≈ 2 МБ на ГБ, 10 ГБ — 20 МБ; в потолке §7.
