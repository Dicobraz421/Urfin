# ADR-0023: собственный движок редактора для файлов любого размера

Статус: **принято владельцем 2026-11-01** (класс B, [решение](../decisions/2026-11-01-editor-engine.md)); ответы на вопросы и одобрение контракта §9 — раздел «Решено владельцем 2026-11-01». Заменяет [ADR-0018](0018-ui-gpui.md) в части «Редактор (S7) — на редакторе gpui-kit» и решение [2026-10-30 «M4» №1](../decisions/2026-10-30-m4.md) (текст редактора в `EditorState` UI). Спека — [S7 §5](../specs/S7.md), карточки S7-26…S7-39.

## Решено владельцем 2026-11-01

Ответы на вопросы PR #243 (класс B, контракт §9 одобрен):
1. **Кодировка внутри** — как в файле (§3), не UTF-8.
2. **Большой файл (> 16 МиБ)** закрывается для записи другим программам **сразу при открытии** (§8 п. 2); пишущийся файл — «Править копию» (п. 3).
3. **История отмены** держится всегда, в том числе после сохранения больших файлов (§4): место старой версии на диске освобождается при закрытии документа.
4. **Подсветка** — только документы ≤ 16 МиБ, больше — без подсветки (§7); «по окнам» — нет. *Заменено 2026-11-02 ([решение](../decisions/2026-11-02-windowed-highlight.md), [ADR-0024](0024-windowed-highlight.md)): подсветка и свёртка — по видимому окну для любого размера; порог 16 МиБ остался только у пакетных языков.*
5. **Блочное выделение — в M4** (Alt+Shift+стрелки и Alt+мышь, как в Far; §7, карточки S7-40/S7-40a); **мультикурсор — после M4**.

## Контекст

- Спайк S7-16 ([docs/perf/s7.md](../perf/s7.md)): `EditorState` gpui-kit держит весь текст в памяти — ≈ 9–10 МБ памяти на МБ текста; `set_value` строит Rope и карту строк на UI-потоке — ≈ 15 мс замирания на МБ. Лимит пришлось поставить 16 МБ; 64 МБ — 1 с без отклика и 600 МБ памяти, 256 МБ — 4 с и 2,4 ГБ.
- Вьювер на своих частях открывает 100 ГБ с первым экраном ≈ 1 мс и памятью «по экрану»: `ByteSource` (S7-02), `PageCache` + `Loader` (S7-03), фоновый `LineIndex` (S7-05), раскладка поверх `ByteView` (S7-06), строки canvas + кэш `ShapedLine` (S7-07), поиск по `Hay` 17 ГБ/с (S7-09).
- Нажатие и прокрутка в `EditorState` в бюджете кадра на любом размере — упирается не кадр, а загрузка и память.

Задача владельца: частичная обработка файла — не жрать память и работать с любым размером.

## Решение

Редактор Урфина для **любого** размера файла — собственный движок в `urfin-view` поверх частей вьювера. `EditorState` gpui-kit из редактора уходит (поля ввода окна — `field.rs` — остаются на gpui-kit). Документ живёт в `view` (handler `editor`), как документ вьювера; UI рисует видимые строки и шлёт ввод.

### 1. Исходный файл не грузится и не меняется до сохранения

- Открытие = открытие вьювера: stat → первые 64 КиБ → детект §3.2 → один кусок `Original(0..len)`. Ни декодирования всего файла, ни Rope. Первый экран — сразу, править можно сразу; номера строк точные, когда фоновый индекс дошёл (до того — «стр ≈N», как во вьювере).
- **Файл ≤ 16 МиБ** читается в память целиком (`Owned`) на Interactive lane и индексируется там же (≈ 10 мс): ссылок на диск у документа нет, внешнее изменение — только конфликт при сохранении (как сейчас, `DiskStamp`).
- **Файл > 16 МиБ** — источник `File` (`seek_read`, свой handle), **не `Mapped`**: отображённый файл мешает `ReplaceFileW`/удалению при сохранении, а на сети и USB ошибка страницы — `EXCEPTION_IN_PAGE_ERROR`. Страницы — через `PageCache` документа (потолок §6). Индекс строк файла — фоновый `Indexer` вьювера.
- Не-локальные VFS (S8) — `Spool` (своя временная копия), правило «только Сохранить как» не меняется.

### 2. Правки — piece table на персистентном дереве

- Документ = последовательность кусков `Piece { src: Src, start: u64, len: u64, lf: Lf }`, `Src = Original | Add | Rewrite(n)` (`Rewrite` — временный файл результата большой «Заменить все» или перевода кодировки, §5), `Lf = Known(u32) | Unknown` (≈ 24 Б на кусок).
- Дерево — **персистентное B+-дерево с узлами в `Arc`** (лист ≤ 64 кусков, узел ≤ 16 детей), суммы в узлах: байты, известные переводы строк, байты кусков с `Lf::Unknown`. Смещение → кусок и строка → кусок — O(log n); вставка и удаление — O(log n) с копированием пути. Как piece tree VS Code, но с `Arc`-узлами (как у ropey): **снимок документа — клон корня, O(1)**. Снимок (`TextSnap: Clone + Send + Sync`) получают поиск, сохранение, подсветка и предпросмотр в фоне, пока пользователь печатает.
- Смежные куски одного источника с непрерывными диапазонами сливаются (набрал и стёр — строка снова «как в файле»). Набор подряд дописывает последний кусок `Add`, а не плодит новые.
- `TextView<'_>` (снимок + кэши страниц) реализует `ByteView` (`cache.rs`), поэтому `layout::{rows_down, row_up, line_start_before, render_row}` работают по документу без изменений; `TextHay` реализует `search::scan::Hay` — движок S7-09 тоже без изменений.
- **Буфер правок `Add`** — только дописывание, блоки по 64 КиБ (`Arc<[u8]>`, срезы стабильны). В памяти — до **16 МиБ**; дальше блоки уходят во временный файл `%TEMP%\Urfin\edit-<pid>-<doc>.add` (`FILE_ATTRIBUTE_TEMPORARY`, `FILE_FLAG_DELETE_ON_CLOSE`) и читаются тем же `PageCache`. Порог: набором его не достичь (16 МиБ — годы печати), его достигают только вставка больших объёмов и «Заменить все» с группами `$1`; 16 МиБ держат документ в потолке §6. Замена без групп — один кусок `Add` на все совпадения (куски могут ссылаться на один диапазон).

### 3. Кодировка внутри — байты в кодировке документа

**Решение:** документ — байты **в одной кодировке документа** (кодировка файла): куски `Original` — как в файле, текст правок (ввод, IME, вставка, замена) кодируется в неё при вводе `encoding_rs::Encoder`. Позиция в документе — байтовое смещение в этой кодировке (у UTF-16 — чётное).

**Почему не «правки в UTF-8, Original декодируется при чтении»** (рекомендация постановки — рассмотрена и отвергнута): документ стал бы смесью двух кодировок, а раскладка (S7-06), индекс (`Sep` на документ), поиск (`compile(pattern, enc)`, HIR-перевод для однобайтовых) и сохранение рассчитаны на одну. Пришлось бы вести строку через границу кодировок во всех этих местах — второй путь кода, который работает только на 1251/866/UTF-16 (редкие файлы — хуже проверены). С одной кодировкой весь код вьювера переиспользуется 1:1, а у UTF-8-файлов (≈ 99 %) варианты совпадают.

Следствия:
- **Сохранение без правок — те же байты** по построению (куски копируются как есть); BOM — флаг документа, кусок `Original` начинается после BOM; EOL не трогаются (как S7-15).
- **Lossy:** недекодируемые байты исходника **сохраняются как были**, пока их не правят (сейчас S7-15 заменяет их при сохранении) — строка `caution` меняет текст.
- **Символа нет в кодировке документа** (эмодзи в 1251, китайский в 866) — вопрос одной строкой при вводе (IME-composition рисуется поверх и в документ не попадает до commit, поэтому вопрос — на commit): «В {enc} нет символа «X»: [Перевести документ в UTF-8] [Вставить «?»] [Отмена]». Перевод — операция с отменой: ≤ 16 МиБ — в памяти за миллисекунды; больше — фоновая задача (поток перекодирования во временный файл `Rewrite`, прогресс, отмена). Кодировка — часть состояния документа в журнале отмены (§4): отмена перевода возвращает и куски, и кодировку.
- `editor.codepage` (F8): без правок — переинтерпретация (перечитать с диска, как сейчас); с правками — кодировка **для сохранения** (как S7-15): сохранение перекодирует потоком, непредставимые — вопрос `EdAsk::Unmappable` (как S7-17).
- UTF-16 (V4): ввод кодируется в UTF-16LE/BE, разделитель строк — `Sep` вьювера; нечётный хвостовой байт — lossy, сохраняется.

### 4. Отмена и повтор — журнал операций

- Операция — `Op::Splice { at, removed: SmallVec<[Piece; 2]>, inserted: SmallVec<[Piece; 2]> }` (текста не копирует: куски ссылаются на `Original`/`Add`) или `Op::Root { before: Root, after: Root, enc }` для массовых правок («Заменить все», `editor.eol`, перевод кодировки, вставка из большого буфера). Отмена применяет обратную операцию.
- Группа — набор операций + выделение до и после. Новая группа — пауза ≥ 1 с, переход курсора (команда движения, мышь), смена вида (ввод ↔ удаление), любая команда правки (вставка, Ctrl+Y, отступ, `editor.md.*`). «Заменить все» и `editor.eol` — одна группа.
- Память журнала — по объёму правок (≈ 24 Б на затронутый кусок + размер `Root`), потолок **16 МиБ**; сверх — отбрасываются старые группы (без вопроса, `tracing`). Счётчика групп нет.
- «Изменён» (●) = позиция в журнале ≠ позиции последнего сохранения: отмена до сохранённого состояния снимает ●, «Отменить/Вернуть» на панели доступны ровно когда есть что отменить (снимает два хвоста S7-16).
- История отмены **переживает сохранение** (как VS Code): куски старых групп ссылаются на старую версию файла через её handle (§8) — место старой версии на диске освобождается при закрытии документа. Исключение — сохранение «на месте» (`nlink > 1`, нет прав на каталог): старых байтов больше нет, группы, ссылающиеся на них, отбрасываются (строка в статусе).

### 5. Поиск и замена — движок S7-09 по кускам

- `TextHay` над снимком: окно 4 МиБ с перекрытием собирается из кусков в буфер (`read_at` источников, не `PageCache`, чтобы не выбивать видимые страницы). `Matcher` S7-09 без изменений: литерал `memmem`, regex по байтам, HIR-перевод для однобайтовых, transcode для UTF-16; `^`/`$` по строкам с CRLF. Свой `regex-cursor` по Rope (S7-18) уходит.
- Счёт совпадений и метки — фоном, как во вьювере (`SearchState`), до `count_limit`.
- «Заменить» (Enter) — обычная правка. **«Заменить все»** — фоновая задача по снимку с прогрессом (≤ 30/с) и отменой (Esc); на время задачи документ только для чтения (статус «Замена 41 %»). Результат — одна группа `Op::Root`:
  - ≤ 64 тыс. совпадений — новые куски (замена без групп — один кусок `Add`, с группами `$1` — текст в `Add`);
  - больше — поток результата во временный файл `Rewrite` (как сохранение): корень — один кусок, память постоянная, на диске — размер документа.

### 6. Память на документ — потолок 64 МиБ

| Часть | Потолок |
|---|---|
| `PageCache` исходника (или сам исходник ≤ 16 МиБ в памяти) | 16 МиБ |
| `Add` в памяти (сверх — временный файл, читается через кэш выше) | 16 МиБ |
| Дерево кусков (≈ 24 Б на кусок + узлы) | ≈ 1 МиБ на 30 тыс. правок; большая «Заменить все» уходит в `Rewrite` |
| Журнал отмены | 16 МиБ |
| Индекс строк файла (метки через 1024 строки) | ≈ 0,2 МиБ на ГБ (10 ГБ — 2 МиБ) |

Не входят: кэш `ShapedLine` UI (2 экрана, как у вьювера) и дерево tree-sitter (только файлы ≤ 16 МиБ; замер — S7-36).

### 7. Рендер и виджет правки (UI)

- **Рендер** — только видимые строки на одном `canvas`, как вьювер: `rows_down` по `TextView`, кэш `ShapedLine` из `rows.rs` (ключ — диапазон, `hscroll`, спека, эпоха стилей, хэш подсветки; правка инвалидирует только свои строки), hit-test `index_for_x` + `RowText.map`. На `Missing` — скелетон и `want()`. Перенос — `WrapKind` S7-06 (`editor.wrap`). **Длинные строки** (V2, 50 МБ одной строкой) — сегменты `max_line` раскладки S7-06; колонка в статусе — точная, если начало строки ближе 1 МиБ, иначе «Кол ≈N».
- Номера строк — из сумм дерева (пока индекс не дошёл — поле пустое, как во вьювере). Полоса изменений — **по кускам, без diff текста**: строка, где только `Add`, — добавлена, `Add` + `Original` — изменена, шов удаления — метка удаления; счётчик в шапке — фоном по списку кусков (O(кусков)). Хэш-diff S7-15 уходит.
- **Мини-карта** 88 — по окну строк вокруг видимой части (как VS Code на длинных файлах): 2 px на строку, ≈ высота/2 строк из страниц кэша (упреждение ± несколько экранов, это десятки КиБ), цвета подсветки, если есть; на длинном документе окно едет пропорционально. Метки поиска и рамка видимой части — пропорционально смещению. Полный текст не нужен.
- **Курсор и выделение** — состояние документа во `view` (`Selections`: курсор + `Stream(Range)` | `Block { lines, cols }`). **Блочное выделение — в M4** (решение владельца): Alt+Shift+стрелки/Home/End/PgUp/PgDn и Alt+drag мышью, как в Far; прямоугольник — логические строки × экранные колонки (табы раскрыты, `unicode-width`). Операции блока: копирование (строки через `eol_new` + формат буфера `MSDEVColumnSelect`, как VS/Notepad++), вырезание и Del/Backspace — удаление колонок в каждой строке (короткие строки не трогаются), ввод — удалить блок и печатать у курсора (как Far), вставка блочного буфера — колонкой от курсора (недостающие строки дописываются), всё одной группой отмены. Блок выше 64 тыс. строк — фоновой задачей через `Rewrite` (как «Заменить все»). **Мультикурсор — после M4**; модель хранит набор выделений, чтобы добавить его без переделки.
- **Клавиши правки и движения — команды** `editor.*` через keymap (§9): переназначаются в пресетах `base`/`far`/`dn`, как всё в Урфине. Движения считает handler по раскладке и `Viewport` (вверх/вниз — по визуальным рядам с памятью колонки, Ctrl+← → — `unicode-segmentation` по окну строки ≤ 64 КиБ). Движение, упёршееся в незагруженные страницы (End на строке 50 МБ, Ctrl+End до конца индекса), завершается по приходу страниц; UI не ждёт.
- **IME** — `EntityInputHandler` GPUI у своего элемента (`ElementInputHandler` в `paint`, `window.handle_input`). Координаты UTF-16 для IME — **локальное окно**: текущая строка, обрезанная до ±2048 единиц UTF-16 вокруг курсора; смещения считаются от начала окна, окно пересобирается при выходе курсора за него. `text_for_range` и `bounds_for_range` — по `RowText` видимых строк (без I/O: строка курсора всегда в кэше; нет — `None`). Marked text (composition) хранится в виджете и рисуется поверх строки с подчёркиванием; в документ и журнал отмены попадает только commit (`replace_text_in_range` → `InboxMsg::Input`). Многострочный ввод (вставка через IME, распознавание речи) — тот же `Input` с переводами строк, нормализованными к `eol_new`.
- **Буфер обмена** — handler, вне UI-потока (`OpenClipboard` может ждать программу-источник): вставка читает `CF_UNICODETEXT` в `view::sys` (Interactive lane) и **потоком** кодирует в `Add` (блоки, выгрузка §2), EOL → `eol_new`, одна группа; копирование и вырезание — до `viewer.copy_limit_mb` (64), больше — тост с размером, вырезание тогда не выполняется.
- Табы и отступы — `tab_size`, `expand_tabs`; Enter — автоотступ (пробелы начала строки, если её начало ближе `max_line`); Ins — режим замены; drag-select — `InboxMsg::Caret { extend }` + автопрокрутка у края.
- **Подсветка** (*заменено [ADR-0024](0024-windowed-highlight.md): видимое окно от контрольных точек, любой размер*) — tree-sitter **напрямую** (`Parser::parse_with` с чтением по снимку), не `SyntaxHighlighter` gpui-kit (ему нужен Rope). Только документы ≤ 16 МиБ (как Разметка вьювера), больше — без подсветки; подсветка «по окнам» для больших — не в M4. Правка → `Tree::edit` (точки строк — из сумм дерева) → разбор в фоне со старым деревом, предыдущий отменяется; запрос подсветки — только видимый диапазон (`QueryCursor::set_byte_range`). UTF-16 — `InputEncoding::UTF16`; однобайтовые — на место не-ASCII байта подаётся ASCII-заглушка (смещения 1:1, разбор по ASCII-синтаксису верен). **Свёртка** — после S7-21, по узлам дерева на видимой части; свёрнутые диапазоны — слой отображения (раскладка их пропускает), не правка.

### 8. Сохранение — потоком; защита исходника

- **Поток:** снимок → куски по очереди (`Original`/`Rewrite` — `read_at` блоками 4 МиБ, `Add` — из памяти/временного файла) → `.<имя>.urfin~` → `sync_all` → `ReplaceFileW` (код S7-17: ACL, атрибуты, потоки, `MoveFileExW` при ошибке, nlink, symlink, права). Память постоянная (≤ 8 МиБ буферов). Кодировка та же — байты копируются; другая (F8 с правками) — перекодирование потоком. Перед записью — свободное место на томе ≥ размер документа (иначе вопрос с цифрами). > 8 МиБ — задача `editor.save` (Bulk, job-бар, отмена), как S7-17.
- Во время сохранения **правка не блокируется** (снимок): если корень не менялся — после записи документ перестраивается на новый файл (один кусок `Original`), иначе куски остаются на старой версии (её handle жив) и ● остаётся.
- Опционально (не в бюджетах): на ReFS / Dev Drive неизменённый префикс до первой правки — block clone (`FSCTL_DUPLICATE_EXTENTS_TO_FILE`, кратно кластеру).

**Внешнее изменение файла** (главный риск: куски `Original` ссылаются на байты файла на диске):

1. **≤ 16 МиБ** — файл в памяти, риска нет; конфликт — `DiskStamp` перед сохранением и при возврате на экран (как S7-17).
2. **> 16 МиБ — запрет записи другим, пока документ открыт:** handle `GENERIC_READ`, share `FILE_SHARE_READ | FILE_SHARE_DELETE` (без `FILE_SHARE_WRITE`). Чужая запись получает «файл занят» (как у Word/Excel); чтение, переименование и удаление разрешены — handle держит байты, которые видел пользователь (удалённый файл живёт до закрытия handle). Замену пути другой программой (git checkout, «сохранить» другого редактора через rename) ловит `DiskStamp` (`file_id`) → «Файл изменён на диске: [Перезагрузить] [Сохранить поверх]», данные документа целы.
3. **Файл уже открыт на запись другой программой** (пишущийся лог) — запрет не получить (`ERROR_SHARING_VIOLATION`): документ открывается без запрета (как вьювер), а первая правка спрашивает одной строкой: «Файл пишет другая программа — правка без запрета записи может испортить текст: [Править копию] [Открыть в просмотре] [Отмена]». «Править копию» — снимок во `%TEMP%` (на ReFS того же тома — block clone, мгновенно; иначе копия задачей с прогрессом), куски ссылаются на снимок; сохранение пишет по исходному пути со сверкой `DiskStamp`.
4. **Своё сохранение при своём handle:** `ReplaceFileW` должен открыть заменяемый файл; есть ли ему право при нашем share без записи — **проверить первым в S7-31** (тест на стенде). Если нет — запасной путь: закрыть handle → `ReplaceFileW` с `lpBackupFileName` (старая версия переименовывается, не удаляется) → открыть резервную копию тем же share и пометить на удаление при закрытии (`FileDispositionInfo`) → журнал отмены остаётся верным. Окно между закрытием и открытием — миллисекунды, файл в это время уже новый.
   **Проверено 2026-11-01 (S7-31, стенд: NTFS, Windows 11 26300; тест `replace_under_own_lock`):** `ReplaceFileW` без резервной копии при нашем handle (`GENERIC_READ`, share `READ | DELETE`) проходит — имя занимает новый файл, прежний handle читает старые байты (место освобождается при его закрытии); `MoveFileExW` при нашем handle — `ERROR_ACCESS_DENIED`. Поэтому handle **не закрывается**; запасной путь (отказ на другой ФС) — `ReplaceFileW` с `lpBackupFileName` и сразу `DeleteFileW` резервной копии (наш share `DELETE` — удаление при закрытии handle), затем `MoveFileExW`.
5. Сеть (SMB) — share mode держит сервер, правило то же. Носитель пропал (USB, сеть) — строки с ошибкой чтения, документ только для чтения, сохранение — только при доступных кусках (иначе ошибка с причиной); риск записан в карточке S7-29.

### 9. Контракт — предложение (класс B)

Меняется строка CONTRACTS «Ввод и клавиатура» про редактор (в PR карточки S7-29, класс B; сейчас там пометка). Было: «Текст редактора — `EditorState` gpui-kit в UI…; события документа (текст принят, изменён, снимок) — `ViewInbox`; `editor.input` нет». Станет:

> Текст редактора — `EditorDoc` в `urfin-view` (piece table, ADR-0023): куски, курсор и выделение, отмена — у handler `editor`. Клавиши правки и движения — команды `editor.*` через keymap (контекст `editor`); набранный текст и commit IME (`InboxMsg::Input`), мышь (`Caret`), окно текста (`Viewport`), прокрутка (`Scroll`, `ScrollTo`) — `ViewInbox` (UI → handler, разбор в `on_pump`), не через Command bus. UI рисует видимые строки из снимка документа (`TextView: ByteView`) и не меняет его; `editor.input` нет.

Строка «Фокус» (`в Editor — editor + global, остальное — виджету`) не меняется: «виджет» — свой элемент правки, он шлёт `Input`.

## Отвергнуто

- **Два режима: gpui-kit до 16 МБ + свой для больших.** Своё нужно всё равно (большие файлы), а gpui-kit добавляет второй редактор с другим undo, IME, поиском, Markdown-командами и полосой изменений — всё делается и проверяется дважды. Файл переходит границу во время правки (вставка 20 МБ) — переключить движок на лету с историей отмены нельзя. Память 9× остаётся на «малых» 16 МБ (≈ 140 МБ на документ).
- **Патчить gpui-kit в pets** (приём готового Rope, карта строк вне UI-потока). Убирает замирание, но не память: весь текст в памяти и ≈ 9× на карты отображения — 10 ГБ не открыть в принципе; патч перебазируется при каждом обновлении gpui-kit (правило владельца — не патчить библиотеки ради лимитов).
- **Rope (ropey) в `view` без gpui-kit.** Rope — тоже весь текст в памяти, декодированный в UTF-8, и O(n) на открытие.
- **Куски по `Mapped` (mmap).** Отображённый файл мешает замене и удалению при сохранении, на сети/USB ошибка страницы — abort; выигрыш 10–30 % по скорости чтения редактору не нужен.
- **Правки в UTF-8 поверх Original в кодировке файла** — §3 (владелец 2026-11-01: кодировка как в файле).
- **Подсветка «по окнам» для документов > 16 МиБ** — владелец 2026-11-01: без подсветки (*пересмотрено 2026-11-02 — [ADR-0024](0024-windowed-highlight.md)*).
- **Снимок всего файла при открытии** вместо запрета записи — 10 ГБ копии на каждое открытие; оставлен только как «Править копию» для файла, который пишет другая программа.
